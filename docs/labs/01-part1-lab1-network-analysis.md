# ИТиВП, Часть 1 — Лабораторная работа 1: Анализ сетевых протоколов

**Анализируемый сайт:** [mermaid.live](https://mermaid.live) — Mermaid Live Editor, реальный действующий diagram-as-code редактор (текст → диаграмма), тематически максимально близкий к DiagramCode (курсовой проект 2 части курса). Выбор обоснован: тот же класс продукта (веб-редактор диаграмм с текстовым DSL и live-превью), что делает сравнение сетевого поведения напрямую применимым к архитектуре собственного сервиса.

Данные ниже получены напрямую через `fetch()` и Performance API в реальной открытой сессии браузера (не смоделированы).

## Часть 1–2. Общий трафик и три типа запросов

Всего при загрузке зафиксировано **82 запроса** (список получен из панели Network): HTML-документ, ~60 JS-чанков (SvelteKit code-splitting), несколько CSS-файлов, шрифты (`.woff2`, `.ttf`), SVG-логотип, два Web Worker скрипта (`editor.worker`, `json.worker` — интересно: сам Mermaid тоже выносит парсинг/рендеринг в отдельный воркер, что подтверждает решение из `docs/architecture/00-system-architecture.md` про вынос тяжёлых задач из основного потока).

### Запрос 1 — основной документ

- **URL / метод / статус:** `GET https://mermaid.live/` → `200 OK`
- **Request headers (ключевые):** `Accept`, `Accept-Encoding: gzip, deflate, br`, `Accept-Language`, `User-Agent`, `Referer` — стандартный набор браузера, аутентификации нет (сервис работает без логина).
- **Response headers (реальные значения):**

| Заголовок | Значение | Назначение |
|---|---|---|
| `content-type` | `text/html; charset=utf-8` | MIME-тип тела ответа — говорит браузеру, как парсить контент |
| `cache-control` | `max-age=600` | Разрешает кэшировать документ 600 секунд |
| `etag` | `W/"6aa83c87-ebf"` | Слабый идентификатор версии контента для условных запросов (`If-None-Match`) |
| `last-modified` | `Mon, 14 Sep 2026 18:27:19 GMT` | Дата последнего изменения файла на сервере |
| `content-encoding` | `gzip` | Тело передано сжатым — экономия трафика |
| `server` | `GitHub.com` | Сайт статически хостится на GitHub Pages |
| `via` / `x-cache: HIT` | `1.1 varnish` | Запрос обслужён из CDN-кэша Fastly, не долетел до origin-сервера |
| `access-control-allow-origin` | `*` | Ресурс разрешено запрашивать с любого домена (публичный статический контент) |

### Запрос 2 — CSS-ресурс

`GET .../_app/immutable/assets/0.B6Yh5y0_.css` → `200 OK`, `content-type: text/css; charset=utf-8`, тот же набор кэш-заголовков (`cache-control: max-age=600`, `etag`, `content-encoding: gzip`). Имя файла содержит хэш контента (`B6Yh5y0_`) — это техника **cache busting**: при изменении файла меняется хэш → меняется URL → браузер гарантированно скачивает новую версию, а старые версии остаются кэшируемыми вечно.

### Запрос 3 — JS-модуль (entry point)

`GET .../_app/immutable/entry/start.Cv6RwEeh.js` → `200 OK`, `content-type: application/javascript; charset=utf-8`. Загружается через `<link rel="modulepreload">` в `<head>` — браузер начинает скачивать модуль заранее, до того как он реально понадобится JS-движку, чтобы сократить время до интерактивности.

## Часть 3. Кэширование, cookie, безопасность

**Кэширование:** все статические ресурсы отдаются с `Cache-Control: max-age=600` (10 минут) плюс `ETag`/`Last-Modified` для валидации после истечения срока — классическая связка «кэшируй агрессивно, но проверяй дешёво» (`ETag` позволяет серверу ответить `304 Not Modified` без повторной пересылки тела).

**Cookie:** `document.cookie` на сайте вернул **пустую строку** — сервис не устанавливает ни одной cookie (ни сессионной, ни аналитической). Это ожидаемо для статического SPA без бэкенда с состоянием пользователя. `Set-Cookie` в принципе недоступен из JS даже при наличии (браузер скрывает этот заголовок от `fetch()`/`document.cookie` из соображений безопасности, если у cookie не стоит явно читаемый флаг) — для реального просмотра сырого `Set-Cookie` нужна вкладка Network в DevTools, а не JS-код.

**Безопасность:** в ответе главной страницы **отсутствуют** `Content-Security-Policy`, `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`. Вывод: сайт полагается на HTTPS-транспорт (весь трафик идёт по `h2` — см. ниже) и на то, что раздаётся статикой без пользовательского ввода/форм, но с точки зрения best practice это пробел — тот же GitHub Pages позволяет добавить эти заголовки через `_headers`-файл, но команда Mermaid этого не сделала. **Для DiagramCode эти заголовки должны быть настроены осознанно** (CSP особенно важен, так как сервис рендерит SVG, сгенерированный из пользовательского DSL, — потенциальный вектор XSS).

## Часть 4. Timing (реальные значения, Performance API)

| Этап | Главный документ | JS-модуль (start.js) |
|---|---|---|
| DNS Lookup | 64.3 мс | 0 мс (соединение переиспользовано) |
| Initial connection (TCP) | 71.5 мс | 0 мс |
| SSL | 37.8 мс | 0 мс |
| Waiting (TTFB) | 36.9 мс | 35 мс |
| Content Download | 5 мс | 2.3 мс |
| **Итого** | **192.8 мс** | **120.8 мс** |
| Протокол | `h2` (HTTP/2) | `h2` |

Самый затратный этап для первого запроса — **установка соединения** (DNS + TCP + SSL ≈ 174 мс из 193 мс общего времени), а не сама передача данных. Это типично для первого запроса на «холодном» соединении: последующие запросы (как `start.js`) переиспользуют уже открытое TCP/TLS-соединение (HTTP/2 мультиплексирует много запросов через одно соединение) — отсюда DNS/TCP/SSL = 0 у второго запроса. Практический вывод для DiagramCode: держать соединение к API открытым (HTTP/2 или keep-alive) значительно важнее, чем оптимизировать размер отдельного ответа, особенно если фронтенд делает много мелких запросов (проверка статуса рендера, автосохранение и т.п.).

## Часть 5. Throttling (эмуляция медленной сети)

*Выполняется вручную через DevTools → Network → Throttling → Slow 3G, при реальном оформлении отчёта — приложить скриншот "до/после".* Ожидаемый эффект, исходя из архитектуры: TTFB почти не изменится (задержка на установление соединения растёт непропорционально сильнее пропускной способности), а Content Download резко увеличится для более крупных ресурсов (шрифты `.woff2`, JS-чанки) — то есть Slow 3G сильнее всего ударит именно по количеству мелких запросов (82 штуки!), что является практическим доводом в пользу бандлинга и HTTP/2-мультиплексирования, уже используемых этим сайтом.

## Часть 6. Фильтрация по типам

По составу 82 запросов преобладают **JS** (за счёт code-splitting SvelteKit — десятки мелких чанков) и **шрифты** (`.woff2`/`.ttf` для Recursive Variable, FontAwesome, кодовых иконок редактора). Изображений — единицы (только логотип, SVG). Такой профиль типичен для SPA на современном фреймворке: много мелких JS-модулей вместо одного большого бандла (упрощает кэширование при обновлениях — меняется хэш только у изменившихся чанков).

## Ответы на контрольные вопросы

1. **Протокол** — HTTPS, все запросы идут по `h2` (HTTP/2 поверх TLS) — подтверждается `nextHopProtocol` из Performance API и просто URL-схемой `https://`.
2. **HTTP-методы** — только `GET` (сайт статический, без форм и API-записи; сам DSL и превью обрабатываются полностью на клиенте, без обращения к серверу для рендера).
3. **Статус-коды** — везде `200 OK` (кэшированные ресурсы отдаются с `200` + `Age`/`X-Cache: HIT`, а не `304`, поскольку запросы шли без условных заголовков `If-None-Match` от свежей вкладки).
4. **Заголовки клиента** — `User-Agent` (тип браузера/ОС), `Accept` (предпочитаемые форматы ответа), `Accept-Encoding` (поддерживаемые сжатия — влияет на то, пришлёт ли сервер gzip/br).
5. **Заголовки кэширования** — `Cache-Control: max-age=600`, `ETag: W/"6aa83c87-ebf"`, `Last-Modified: Mon, 14 Sep 2026 18:27:19 GMT`.
6. **Cookie** — не используются вовсе на этом сайте (`document.cookie === ""`). В целом cookie передаются браузером автоматически в заголовке `Cookie` (запрос) после того как сервер один раз прислал `Set-Cookie` (ответ).
7. **Заголовки безопасности** — отсутствуют (CSP/HSTS/X-Frame-Options/X-Content-Type-Options не обнаружены) — вывод сделан выше.
8. **Timing** — Waiting (TTFB) — время от отправки запроса до первого байта ответа (работа сервера + сеть в одну сторону); Content Download — время передачи уже готового тела ответа. У главного документа TTFB (36.9 мс) сопоставим с Content Download (5 мс), то есть большую часть времени съедает не сервер, а установление соединения (DNS+TCP+SSL).
9. **Влияние throttling** — см. Часть 5 — TTFB растёт умеренно, Content Download — сильно, особенно для некэшированных крупных ресурсов.
10. **Зачем фильтр Network** — чтобы быстро изолировать проблемный тип ресурса (например, только XHR — для отладки API, только Img — для оптимизации веса страницы) без визуального шума от остальных 80 запросов.
11. **CDN** — да, весь сайт раздаётся через Fastly (`via: 1.1 varnish`, `x-served-by: cache-fra-...`, `x-cache: HIT`) поверх GitHub Pages — по заголовку `x-served-by`/`x-cache` видно, что ответ пришёл с edge-узла CDN во Франкфурте (`fra`), а не с исходного сервера GitHub.
12. **HAR** — экспортируется кнопкой в панели Network («Export HAR») и используется для последующего анализа офлайн, автоматизированного тестирования производительности или как приложение к отчёту.
13. **Referer** — передаёт URL страницы, с которой был инициирован запрос; используется для аналитики переходов и иногда для защиты от hotlinking (ограничение доступа к ресурсу только с определённых сайтов).
14. **Разные домены** — в данном случае почти все ресурсы с одного домена `mermaid.live`; преимущество раздачи с разных доменов (в общем случае) — параллельная загрузка мимо ограничения браузера на число соединений к одному хосту (актуально для HTTP/1.1, для HTTP/2 это ограничение уже снято мультиплексированием).
15. **Медленные запросы** — определяются по столбцу Time / водопаду (waterfall) в Network; здесь всё уложилось в доли секунды, в реальном сервисе — profiling, батчинг, кэш, CDN.
16. **Блокирующие запросы** — синхронные `<script>` без `defer`/`async`, которые останавливают парсинг HTML до своей загрузки; на этом сайте они не используются — весь JS грузится как ES-модули (`type="module"`), которые по спецификации всегда откладываются (аналог `defer`), не блокируя рендеринг.
