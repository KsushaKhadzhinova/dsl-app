## 1 ЦЕЛЬ РАБОТЫ

Освоение управления состоянием в приложении на *React*: локальное состояние компонентов через
*useState* и побочные эффекты через *useEffect*, а также состояние, разделяемое между
несколькими компонентами без передачи через цепочку *props* (*prop drilling*), через *Context
API* в связке с *useReducer*. В рамках лабораторной работы создан новый клиентский проект
`client/` для курсового проекта *DiagramCode* — отдельный от `frontend/`, реализующий реальные
экраны для ресурса «Диаграмма» поверх уже готового серверного *REST API* (лабораторные работы
№1–3): список, просмотр одной диаграммы, создание, редактирование, удаление.

## 2 ХОД РАБОТЫ

### 2.1 Структура нового клиента

Проект создан через *Vite* (`npm create vite@latest client -- --template react`) в папке
`client/` в корне репозитория — рядом с уже существующим `frontend/`, который относится к
отдельному продуктовому приложению и не затрагивается этой веткой. Слой обращения к серверному
*API* вынесен в `client/src/api/`: `client.js` содержит общую функцию `apiFetch`, оборачивающую

модуль `client/src/auth/token.js` — выделение этой логики в отдельный *AuthContext* является
задачей практики №4 и сознательно не выполняется здесь, чтобы не забегать вперёд.

### 2.2 Локальное состояние: *useState* и *useEffect*

Формы входа (`LoginForm`), регистрации (`RegisterForm`) и создания/редактирования диаграммы
(`DiagramForm`) используют *useState* для каждого поля ввода (*email*, пароль, *title*,
*notation*, *dslContent*) и для локального состояния отправки формы (*submitting*, *error*) —
это состояние нужно только внутри самой формы и не должно "протекать" наружу через *props*.
Навигация между экранами внутри приложения (список / просмотр / создание / редактирование) в
`App.jsx` тоже реализована через простой *useState* с именем экрана, поскольку *React Router* —
предмет отдельной практики №3, которая будет выполнена в следующей ветке этой цепочки.

### 2.3 *Context API* + *useReducer*: `DiagramsContext`

Список диаграмм, состояние загрузки и текст ошибки — это состояние, нужное одновременно
нескольким независимым компонентам (`DiagramList`, `DiagramDetail`, обработчикам форм в
`App.jsx`), то есть классический случай, где передача через *props* потребовала бы прокидывать
данные и функции через компоненты, которым они самим не нужны (*prop drilling*). Вместо этого
состояние вынесено в `DiagramsContext` (`client/src/context/DiagramsContext.jsx`), использующий
*useReducer* с чистой функцией-редьюсером в отдельном файле `diagramsReducer.js` — отдельно от
компонента-провайдера, чтобы редьюсер можно было протестировать без рендеринга *React*-дерева.

Редьюсер поддерживает шесть типов действий: `FETCH_START`/`FETCH_SUCCESS`/`FETCH_ERROR` —
жизненный цикл загрузки списка диаграмм с сервера, `ADD_DIAGRAM`/`UPDATE_DIAGRAM`/
`REMOVE_DIAGRAM` — локальное обновление списка после успешного ответа сервера на создание,
редактирование или удаление (без повторного полного перезапроса списка), и `SET_LAST_VIEWED_ID`
— см. раздел 2.4. Провайдер `DiagramsProvider` оборачивает дерево экранов, доступных только
авторизованному пользователю, и предоставляет через *context* не только само состояние, но и
функции `refresh`, `addDiagram`, `editDiagram`, `removeDiagram`, `setLastViewedId`, каждая из
которых вызывает соответствующую функцию из `diagramsApi.js` и затем *dispatch*'ит результат.

### 2.4 Побочный эффект: запоминание последней просмотренной диаграммы

Кроме обязательного *useEffect* для начальной загрузки списка диаграмм при монтировании
`DiagramsProvider` (вызов `refresh()` один раз), реализован второй, содержательный побочный
эффект: идентификатор последней просмотренной диаграммы сохраняется в `localStorage` под ключом
`lastViewedDiagramId`. Начальное значение состояния читается из `localStorage` при инициализации
редьюсера (через ленивый инициализатор `useReducer`), а отдельный *useEffect*, зависящий от
`state.lastViewedId`, записывает новое значение в `localStorage` при каждом его изменении —
происходящем при открытии экрана просмотра диаграммы (`DiagramDetail`). Это позволяет — например,
после перезагрузки страницы — знать, какая диаграмма была открыта последней, не обращаясь к
серверу.

### 2.5 Тестирование

Для нового кода написаны тесты на *Jest* + *React Testing Library* в `client/tests/`:
`diagramsReducer.test.js` проверяет каждый тип действия редьюсера как чистую функцию (без
рендеринга компонентов) — начальное состояние, переходы `FETCH_START`/`FETCH_SUCCESS`/
`FETCH_ERROR`, обновление списка при `ADD_DIAGRAM`/`UPDATE_DIAGRAM`/`REMOVE_DIAGRAM`, обновление
`lastViewedId`, и то, что неизвестное действие не меняет состояние. `DiagramsContext.test.jsx`
тестирует сам провайдер через тестовый компонент-потребитель контекста с замоканным глобальным
*fetch*: успешная начальная загрузка списка, отображение ошибки при неудачном ответе сервера,
добавление диаграммы через `addDiagram`, запись `lastViewedId` в `localStorage`.
`DiagramList.test.jsx` и `DiagramForm.test.jsx` проверяют поведение компонентов списка и формы:
состояния загрузки/пустого списка/заполненного списка, обработчики выбора и создания диаграммы,
удаление элемента из списка, предзаполнение формы значениями при редактировании, вызов
*callback*-а `onSubmit` с текущими значениями полей, отображение ошибки при отклонённом
*promise*. Библиотека компонентов *Material-UI*, упомянутая в задании как опциональная, не
подключалась — экраны собраны на обычных *HTML*-элементах и минимальном *CSS*, чтобы не
усложнять проект сверх того, что требует задание.

## 3 ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

1. В чём разница между *useState* и *useReducer*?
*useState* хранит одно независимое значение и обновляется напрямую вызовом функции-*setter*, что
удобно для простых, не связанных друг с другом полей (например, значения одного поля ввода).
*useReducer* хранит состояние, части которого меняются согласованно по определённым правилам
(*actions*), и обновляется только через чистую функцию-редьюсер — это яснее выражает "что
произошло" (*action.type*), а не "как именно поменять состояние", и упрощает тестирование
логики переходов состояния отдельно от компонентов.

2. Что такое *prop drilling* и как *Context API* решает эту проблему?
*Prop drilling* — ситуация, когда данные или функции передаются через *props* сквозь несколько
уровней компонентов, которым эти данные сами не нужны, только чтобы передать их дальше, вглубь
дерева. *Context API* позволяет объявить значение один раз в компоненте-провайдере и получить
его напрямую в любом потомке через хук *useContext*, без промежуточных передач.

3. Почему в проекте редьюсер (`diagramsReducer.js`) вынесен в отдельный файл от
компонента-провайдера?
Редьюсер — чистая функция (*state*, *action*) → новое состояние, не зависящая от *React* и
хуков. Вынос в отдельный файл позволяет тестировать все переходы состояния напрямую, вызывая
функцию с разными действиями, без необходимости монтировать *React*-компоненты и имитировать
асинхронные сетевые запросы.

4. Зачем нужен второй, "содержательный" побочный эффект в лабораторной работе, помимо загрузки
данных при монтировании?
Чтобы показать, что *useEffect* используется не только для начальной загрузки данных с сервера,
а в целом для синхронизации состояния компонента с чем-то внешним по отношению к *React* — в
данном случае с `localStorage`, куда при каждом изменении `lastViewedId` записывается новое
значение, и откуда оно же читается при первой инициализации состояния.

5. Почему функции `addDiagram`/`editDiagram`/`removeDiagram` в `DiagramsContext` обёрнуты в
*useCallback*?
Значение контекста (`value`) — новый объект при каждом рендере провайдера; без *useCallback*
входящие в него функции тоже создавались бы заново при каждом рендере, что могло бы приводить к
лишним повторным рендерам потребителей контекста, зависящих от этих функций (например, в
зависимостях чужого *useEffect*). *useCallback* сохраняет ссылочную стабильность функции между
рендерами, если её собственные зависимости не изменились.

## ВЫВОДЫ

В результате выполнения лабораторной работы создан новый клиентский *React*-проект `client/`
курсового проекта *DiagramCode*, реализующий реальные экраны *CRUD* для ресурса «Диаграмма»
поверх уже готового серверного *API* с *JWT*-аутентификацией — без мок-данных и без разделения
диаграмм по владению между пользователями, в соответствии с решением, принятым в лабораторной
работе №3. Локальное состояние форм и навигации реализовано через *useState*, а состояние
списка диаграмм, разделяемое между несколькими компонентами, — через *Context API* и
*useReducer* с редьюсером, вынесенным в отдельный тестируемый файл. Побочные эффекты (*useEffect*)
покрывают как обязательную начальную загрузку данных с сервера, так и содержательную
синхронизацию с `localStorage` для запоминания последней просмотренной диаграммы. Написаны
автоматические тесты на *Jest* + *React Testing Library*, покрывающие все типы действий
редьюсера, поведение провайдера контекста и ключевые сценарии компонентов списка и формы.
Разделение токена и авторизации на отдельный *AuthContext*, а также маршрутизация через *React
Router*, — задачи следующих практик (№3 и №4) этой же цепочки веток.
