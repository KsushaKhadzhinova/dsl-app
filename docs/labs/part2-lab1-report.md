## 1 ЦЕЛЬ РАБОТЫ

Приобретение практических навыков создания серверного приложения на платформе *Node*.*js*
с использованием фреймворка *Express*.*js*. Изучение основ маршрутизации, обработки

## 2 ХОД РАБОТЫ

### 2.1 Обзор предметной области

В качестве предметной области выбран сервис *DiagramCode* — веб-приложение для описания и
визуализации диаграмм на собственном текстовом языке (*DSL*): *UML*, *BPMN*, *ERD*, сети
Петри, *IDEF*0/*IDEF*3, *DFD*. Подобные системы востребованы там, где диаграмму удобнее
хранить и версионировать как текст, а не как графический файл: в документации распределённых
систем, при проектировании бизнес-процессов, в учебных курсах по моделированию.

Основная информационная сущность приложения — «Диаграмма» (*Diagram*). Согласно
реализованной модели данных, каждая диаграмма характеризуется атрибутами: *id* — числовой
идентификатор, автоматически увеличивающийся (*autoincrement*) при создании новой записи в
памяти сервера; *title* — название диаграммы, обязательное поле; *notation* — нотация
диаграммы (например, *erd*, *bpmn*, *uml*), обязательное поле; *dslContent* — текстовое
*DSL*-описание диаграммы, необязательное поле, по умолчанию пустая строка; *createdAt* —
дата и время создания записи в формате *ISO*, проставляется автоматически.

Архитектура построена по модульному принципу с разделением на маршруты (*routes*),
контроллеры (*controllers*) и модели (*models*). Все запросы к ресурсу диаграмм
обрабатываются по базовому *URL*-пути /*diagrams*.

### 2.2 Теоретические сведения

*Node*.*js* — программная платформа на движке *V*8 (*Google*), выполняющая *JavaScript*-код
вне браузера, на стороне сервера. Ключевые архитектурные особенности — модульная система
(*CommonJS*: *require*/*module*.*exports*) и асинхронная, событийно-ориентированная модель
выполнения на едином потоке.

*Express*.*js* — минималистичный фреймворк поверх *Node*.*js* для построения веб-серверов.
Приложение создаётся вызовом функции *express*(), которая возвращает объект *app* с методами
конфигурации, запуска (*app*.*listen*()) и маршрутизации *HTTP*-запросов.

Центральные концепции *Express* — маршрутизация (*routing*: связка *URL* + *HTTP*-метод с
функцией-обработчиком) и *middleware* — функции вида (*req*, *res*, *next*), выполняющиеся
последовательно в порядке регистрации через *app*.*use*(); обработчики ошибок — их частный
случай с сигнатурой (*err*, *req*, *res*, *next*).

### 2.3 Настройка среды разработки и структуры проекта

В качестве *IDE* использовался *VS Code*; для работы сервера установлены *Node*.*js* (*LTS*)
и *npm*. (Рисунок 2.1 — проверка версий `node --version` / `npm --version` в терминале
*VS Code* — свой скриншот.)

Проект организован по слоям и включает точку входа и четыре специализированные директории.
Корневой файл *server*.*js* является точкой входа в приложение: он создаёт экземпляр сервера
через фабричную функцию *createApp*() и запускает прослушивание сетевого порта вызовом
*app*.*listen*(*port*). Сама сборка *Express*-приложения вынесена в отдельный файл *app*.*js*,
который подключает встроенный *middleware* *express*.*json*() для разбора тела входящих
запросов, монтирует маршруты ресурса диаграмм по базовому пути /*diagrams*, а также
регистрирует последними два обработчика — *notFoundHandler* для несуществующих маршрутов и
*errorHandler* для прочих ошибок; такое разделение на *server*.*js* и *app*.*js* сделано
намеренно, чтобы собранное приложение можно было использовать в тестах без реального
прослушивания порта.

(Рисунок 2.2 — структура проекта в проводнике *VS Code* — свой скриншот.)

Директория *routes* содержит файл *diagramRoutes*.*js*, который связывает *HTTP*-методы и
*URL*-пути с соответствующими функциями контроллера, не описывая при этом никакой
бизнес-логики самостоятельно. Директория *controllers* содержит файл *diagramController*.*js*
— слой бизнес-логики, в котором реализованы пять *CRUD*-функций (*getAll*, *getById*,
*create*, *update*, *remove*) и вспомогательная функция *validatePayload*, проверяющая, что
обязательные поля *title* и *notation* присутствуют и являются непустыми строками. Директория
*models* содержит файл *diagramStore*.*js* — слой представления данных, реализующий
хранилище диаграмм в виде массива в оперативной памяти процесса с функциями *findAll*,
*findById*, *create*, *update* и *remove*. Отдельная директория *middleware* содержит файл
*errorHandler*.*js* с двумя обработчиками: первый возвращает статус 404 для любого маршрута,
не описанного в приложении, второй перехватывает ошибки, переданные через *next*(*err*), и
возвращает статус 500. Наконец, директория *tests* содержит автоматические тесты, написанные
с использованием *Jest* и *Supertest*, которые проверяют работу всех пяти маршрутов и по
итогу дают стопроцентное покрытие кода.

### 2.4 Реализация и тестирование эндпоинтов

Для взаимодействия с коллекцией диаграмм был спроектирован и реализован *REST API*,
состоящий из пяти маршрутов. Таблица 2.1 обобщает используемые *HTTP*-методы, ожидаемые
статусы ответов и примеры передаваемых и возвращаемых данных.

**Таблица 2.1 — маршруты *API***

| Маршрут | Метод | Ожидаемый статус | Тело запроса | Пример ответа |
|---|---|---|---|---|
| /*diagrams* | *GET* | 200 *OK* | отсутствует | `[{"id":1,"title":"Схема заказов","notation":"erd","dslContent":"","createdAt":"2026-09-16T18:00:00.000Z"}]` |
| /*diagrams*/:*id* | *GET* | 200 *OK* / 404 *Not Found* | отсутствует | `{"id":1,"title":"Схема заказов","notation":"erd","dslContent":"","createdAt":"..."}` |
| /*diagrams* | *POST* | 201 *Created* / 400 *Bad Request* | `{"title":"Схема заказов","notation":"erd"}` | `{"id":1,"title":"Схема заказов","notation":"erd","dslContent":"","createdAt":"..."}` |
| /*diagrams*/:*id* | *PUT* | 200 *OK* / 400 / 404 | `{"title":"Обновлённая схема","notation":"bpmn"}` | `{"id":1,"title":"Обновлённая схема","notation":"bpmn","dslContent":"","createdAt":"..."}` |
| /*diagrams*/:*id* | *DELETE* | 204 *No Content* / 404 | отсутствует | пустое тело ответа |

Для проверки работоспособности *REST API* использовалась среда *Postman*. Ниже подробно
описано тестирование каждого эндпоинта для базовых операций *CRUD*.

Операция чтения всей коллекции, реализованная посредством *HTTP*-метода *GET* по адресу
/*diagrams*, предназначена для получения массива всех диаграмм, которые на текущий момент
хранятся в памяти сервера. Запрос выполняется без передачи данных в теле, контроллер *getAll*
просто вызывает *store*.*findAll*() и сериализует полученный массив в *JSON*; в случае
успешной обработки сервер всегда возвращает статус 200 *OK*, поскольку даже пустая коллекция
диаграмм считается корректным, не ошибочным результатом. (Рисунок 2.3 — свой скриншот.)

Операция получения одной диаграммы по идентификатору выполняется посредством *GET*-запроса к
эндпоинту /*diagrams*/:*id*. Контроллер *getById* извлекает переданный в *URL* параметр через
*req*.*params*.*id*, приводит его к числу и ищет соответствующий объект в массиве с помощью
*store*.*findById*. Если диаграмма с таким *id* существует, сервер возвращает её в теле ответа
со статусом 200 *OK*; если диаграмма не найдена — явно возвращается статус 404 *Not Found* с
телом `{"error":"Диаграмма не найдена"}`, а не пустой либо неопределённый результат, что важно
для предсказуемого поведения клиента. (Рисунок 2.5 — свой скриншот.)

Операция создания реализуется через *HTTP*-метод *POST* с передачей данных новой диаграммы в
теле запроса в формате *JSON*. Перед сохранением контроллер *create* вызывает
*validatePayload*, которая проверяет, что поля *title* и *notation* присутствуют и являются
непустыми строками; если хотя бы одно из условий не выполнено, сервер немедленно возвращает
статус 400 *Bad Request* с текстом ошибки, не обращаясь к хранилищу вовсе. При успешной
валидации *store*.*create* формирует новый объект диаграммы, присваивает ему автоматически
увеличивающийся числовой *id*, подставляет пустую строку для необязательного поля
*dslContent*, если оно не передано, проставляет текущую дату и время в поле *createdAt* и
добавляет запись в массив; клиенту возвращается статус 201 *Created* вместе с созданным
объектом. (Рисунок 2.4 — свой скриншот.)

Операция обновления реализуется через *HTTP*-метод *PUT* и предназначена для полной
перезаписи существующего ресурса по переданному идентификатору. Так же, как и при создании,
входные данные сперва проходят через *validatePayload* — обновлённые *title* и *notation*
обязательны, поскольку *PUT* подразумевает замену ресурса целиком, а не частичное изменение
отдельных полей. Если валидация не пройдена, возвращается 400 *Bad Request*; если диаграмма с
указанным *id* не найдена в хранилище, контроллер возвращает 404 *Not Found*; при успешном
выполнении обоих условий *store*.*update* перезаписывает поля найденного объекта и возвращает
его со статусом 200 *OK*. Оба сценария — успешное обновление и попытка обновить
несуществующую диаграмму — были протестированы отдельно. (Рисунки 2.6 успех / 2.7 404 — свои
скриншоты.)

Операция удаления реализуется через *HTTP*-метод *DELETE* и предназначена для удаления
диаграммы из хранилища по указанному идентификатору. Контроллер *remove* вызывает
*store*.*remove*, которая ищет индекс записи в массиве и, если запись найдена, удаляет её
методом *splice* и возвращает *true*; в этом случае сервер отвечает статусом 204 *No Content*
без какого-либо тела ответа, поскольку удалённый ресурс уже не существует и возвращать нечего.
Если запись с таким *id* не найдена, *store*.*remove* возвращает *false*, и контроллер
отвечает статусом 404 *Not Found*. Отдельно был протестирован сценарий повторного удаления уже
удалённой диаграммы — сервер корректно возвращает 404 вместо повторного 204, что подтверждает
отсутствие ложного успеха при отсутствующем ресурсе. (Рисунок 2.8 — свой скриншот.)

## 3 ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

**1. Какие методы *HTTP* вы реализовали и для каких операций?**
Были реализованы методы *GET* для получения списка всех диаграмм и одной по *id*, *POST* для
создания новой диаграммы, *PUT* для полного обновления данных существующей диаграммы и
*DELETE* для удаления диаграммы.

**2. Как получить параметры из *URL* (*route params*) и строку запроса (*query string*) в
*Express*?**
Параметры из пути *URL* (например, *id* в маршруте /*diagrams*/:*id*) извлекаются через
объект *req*.*params*.*id*. Данные из строки запроса (то, что передаётся после знака вопроса,
например ?*sort*=*title*) извлекаются через объект *req*.*query*.

**3. Для чего используется *middleware* *express*.*json*()?**
Этот встроенный *middleware* необходим для автоматического разбора входящих *HTTP*-запросов,
заголовок *Content*-*Type* которых установлен как *application*/*json*. Он преобразует
*JSON*-строку в объект *JavaScript*, доступный в коде через *req*.*body*.

**4. Какой *HTTP*-статус возвращается при успешном создании ресурса? При успешном удалении?**
При успешном создании ресурса (*POST*) возвращается статус 201 *Created*. При успешном
удалении (*DELETE*) возвращается статус 204 *No Content* (сервер успешно обработал запрос, но
в ответе не передаёт никакого содержимого).

**5. Что такое *REST API*? Перечислите основные принципы *REST*.**
*REST API* — это архитектурный стиль взаимодействия компонентов распределённого приложения по
протоколу *HTTP*. Основные принципы: клиент-серверная архитектура (разделение фронтенда и
бэкенда), отсутствие состояния на сервере (*Stateless* — каждый запрос содержит все необходимые
данные), кэшируемость ответов, единообразие интерфейса (использование стандартных
*HTTP*-методов и *URI*) и многоуровневая система.

**6. Как организовать глобальную обработку ошибок в *Express*?**
Для этого создаётся специальная функция *middleware*, принимающая ровно 4 аргумента: (*err*,
*req*, *res*, *next*). В данном проекте это функция *errorHandler*, зарегистрированная через
*app*.*use*() в самом конце файла *app*.*js*, после всех маршрутов и после *notFoundHandler*.

**7. Какую структуру ответа сервера вы выбрали для ошибок?**
Для ответа при возникновении ошибок используется стандартизированный *JSON*-объект с одним
полем *error*, содержащим текстовое описание проблемы.

**8. Как протестировать *DELETE*-запрос, если ресурс уже был удалён? Какой статус должен быть
возвращён?**
Необходимо повторно отправить *DELETE*-запрос на тот же *URL* (например, /*diagrams*/1) через
*Postman*. Поскольку ресурса в массиве больше нет, сервер не сможет его найти и должен вернуть
статус 404 *Not Found*.

**9. Какие преимущества даёт использование *nodemon* в процессе разработки?**
*Nodemon* автоматически отслеживает любые изменения в файлах проекта и перезапускает
*Node*.*js* сервер. Это избавляет разработчика от необходимости вручную останавливать и заново
запускать сервер после каждого изменения кода.

**10. В чём разница между методами *PUT* и *PATCH*? Какой из них вы реализовали и почему?**
Метод *PUT* используется для полной замены существующего ресурса новыми данными. Метод
*PATCH* используется для частичного изменения ресурса (передаются только те поля, которые
нужно обновить). В данной работе реализован метод *PUT*, так как по заданию требовалось
реализовать операцию полного обновления диаграммы.

**11. Как можно добавить поддержку *CORS* в ваше приложение? (теоретически)**
Необходимо установить пакет *cors* командой *npm install cors*, затем импортировать его в
*app*.*js* (*const cors* = *require*('*cors*');) и подключить как глобальный *middleware*:
*app*.*use*(*cors*());. Это разрешит браузерам делать запросы к *API* с других доменов.

**12. Почему в данном задании данные хранятся в массиве, а не в базе данных? Когда стоит
переходить на БД?**
Хранение в массиве используется на начальном этапе для изучения основ маршрутизации и
принципов работы *HTTP*. На полноценную БД стоит переходить, когда требуется надёжное хранение
данных, которое не будет удаляться при перезагрузке сервера, а также для работы со сложными
связями и большими объёмами информации — это и реализовано в следующей лабораторной работе
через *Sequelize* и *PostgreSQL*.

**13. Какой заголовок *Content*-*Type* должен быть установлен для отправки *JSON*-данных?**
Должен быть установлен заголовок *Content*-*Type*: *application*/*json*.

**14. Напишите пример *curl*-команды для тестирования вашего *POST*-эндпоинта.**
*curl* -*X POST http*://*localhost*:3000/*diagrams* -*H* "*Content*-*Type*:
*application*/*json*" -*d* "{\"*title*\":\"Схема заказов\",\"*notation*\":\"*erd*\"}"

**15. Как убедиться, что сервер работает корректно после каждой модификации кода?**
Следует посмотреть в консоль терминала на предмет отсутствия синтаксических ошибок (*nodemon*
выведет сообщение о перезапуске сервера) и выполнить соответствующие запросы через *Postman*,
чтобы убедиться, что сервер возвращает ожидаемые статус-коды и *JSON*-данные.

**16. Какие шаги нужно предпринять, чтобы запустить ваше приложение на другом компьютере?**
Скопировать файлы проекта (обязательно исключив тяжёлую папку *node*_*modules*). На новом
компьютере открыть проект в терминале, выполнить команду *npm install* (она прочитает
*package*.*json* и скачает все нужные библиотеки), после чего запустить сервер командой
*npm run dev* или *npm start*.

## ПРИЛОЖЕНИЕ А (обязательное). Листинг файлов *app*.*js* и *server*.*js*

```js
// app.js
const express = require("express");
const diagramRoutes = require("./routes/diagramRoutes");
const { notFoundHandler, errorHandler } = require("./middleware/errorHandler");

function createApp() {
  const app = express();
  app.use(express.json());
  app.use("/diagrams", diagramRoutes);
  app.use(notFoundHandler);
  app.use(errorHandler);
  return app;
}

module.exports = createApp;
```

```js
// server.js
const createApp = require("./app");

const port = process.env.PORT || 3000;
const app = createApp();

app.listen(port, () => console.log(`Server running on port ${port}`));
```
