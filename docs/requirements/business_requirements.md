# Бизнес-требования (Business Requirements)

**Статус:** актуально
**Отличие от функциональных требований:** здесь — что должно быть верно для бизнеса/проекта в целом (высокий уровень, независимо от конкретной реализации). Как именно система это обеспечивает технически — в `01-functional-requirements.md`.

| ID | Бизнес-требование | Обоснование |
|---|---|---|
| BR-01 | Система должна позволять пользователю описывать диаграммы текстом (DSL), а не только графическим редактором | Основная идея продукта — «diagram as code»; отличает от draw.io-подобных инструментов |
| BR-02 | Система должна поддерживать несколько семейств нотаций (инженерные — UML/ERD/BPMN — и методологические — IDEF/DFD/сети Петри) | Ни один конкурент не покрывает оба семейства одновременно (см. анализ рынка) — это единственная реальная рыночная ниша проекта |
| BR-03 | История изменений диаграммы должна сохраняться так же надёжно, как история кода в git | Диаграмма — такой же артефакт разработки, как код, и должна версионироваться на том же уровне доверия |
| BR-04 | Система должна снижать порог входа через AI-генерацию по тексту/изображению | Написание DSL с нуля — барьер для нового пользователя; готовый черновик снижает этот барьер |
| BR-05 | Стоимость эксплуатации на этапе учебного проекта должна быть нулевой | Проект не имеет бюджета — обязательное ограничение, не пожелание |
| BR-06 | Архитектура должна допускать добавление нотаций/интеграций без пересмотра ядра | Иначе стоимость расширения растёт с каждой новой нотацией нелинейно |
| BR-07 | Курсовой срез должен быть честным подмножеством целевой системы, а не отдельной демо-заглушкой | Требование методички + защита от риска «два разных проекта под одной обёрткой» |
| BR-08 | Все отчётные и демонстрационные материалы должны отражать реальное поведение системы | Академическая честность — жёсткое ограничение проекта, не опция |
