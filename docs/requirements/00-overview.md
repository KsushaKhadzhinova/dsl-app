# Требования к системе DiagramCode — обзор и правила чтения

**Статус:** актуально
**Связанные документы:** [`docs/architecture/00-system-architecture.md`](../architecture/00-system-architecture.md), [`docs/architecture/01-ai-provider-setup.md`](../architecture/01-ai-provider-setup.md), [`docs/labs/00-labs-mapping.md`](../labs/00-labs-mapping.md)

Этот документ и два соседних (`01-functional-requirements.md`, `02-nonfunctional-requirements.md`) фиксируют требования к DiagramCode так, как они уже вытекают из принятых архитектурных решений, макетов интерфейса (`design/mockups/*.dc.html`) и фактического кода (`backend/app/`). Здесь **не изобретаются новые решения** — документ систематизирует то, что уже согласовано, и явно помечает те немногие места, где решения ещё не принято (раздел «Открытые вопросы» ниже).

---

## 1. Два среза требований

Как и в архитектуре (см. §1 `00-system-architecture.md`), требования существуют в двух срезах:

- **Целевые требования** — полный охват: все нотации (UML, ERD, IDEF0/1X/3, DFD, после MVP — BPMN и сети Петри), AI, все три способа хранения, полная валидация. Помечены волной реализации (Волна 1–4).
- **Курсовой срез** — подмножество, достаточное для защиты курсовой работы (3 обязательных модуля РПЗ за ~30 часов): DSL-редактор + рендер + сохранение + одна нотация (`erd.crows_foot.logical`) с валидацией + аутентификация. Это Волна 1.

Каждое функциональное требование (FR) в `01-functional-requirements.md` помечено тегом волны:

| Тег | Значение | Ссылка на архитектуру |
|---|---|---|
| `[Волна 1 / MVP]` | Курсовой срез — уже частично реализовано в `backend/app/` | §5, "Волна 1" |
| `[Волна 2]` | Следующие нотации и режимы после защиты | §5, "Волна 2" |
| `[Волна 3]` | Полное покрытие UML/ERD/IDEF | §5, "Волна 3" |
| `[Волна 4 / после MVP]` | BPMN и сети Петри | §5, "Волна 4" |

Нефункциональные требования (NFR) волной не помечаются — они действуют на систему в целом с самого начала (даже если конкретный NFR полностью проверяем только после реализации соответствующей волны FR).

## 2. Источники требований

Каждое требование в этих документах опирается на один или несколько источников:

1. **Архитектурные решения** — `docs/architecture/00-system-architecture.md`, `01-ai-provider-setup.md`.
2. **Макеты интерфейса** — 13 файлов в `design/mockups/*.dc.html`: `IDE-Dark`, `IDE-Light`, `Login`, `AIImageUpload`, `AIModalText`, `AIResultBPMN`, `DiffView`, `DocumentationModal`, `PanelResize`, `SaveDropdown`, `SidebarDetail`, `Validation`, `VersionHistory`. Эти макеты — не просто иллюстрации: они содержат конкретные детали поведения (список статусов в статус-баре, состав дропдауна сохранения, вкладки AI-модалки, структура таблицы истории версий и т.д.), которые нигде больше текстом не зафиксированы — поэтому FR по UI прямо ссылаются на конкретный файл макета.
3. **Существующий код** — `backend/app/` (домен, DSL-парсер, нотация ERD, репозитории, сервисы, роуты) и `backend/tests/` — фиксирует уже работающее поведение как требование (не наоборот).
4. **Официальная методичка ИТиВП** (`Часть 2/Курсовое проектирование/03. Структура пояснительной записки к курсовой работе.pdf`) — формат «Пользователь может…» для FR и раздел NFR (производительность/безопасность/адаптивность) заимствован оттуда для совместимости с шаблоном РПЗ.

## 3. Действующие лица (акторы)

| Актор | Описание |
|---|---|
| **Пользователь** | Зарегистрированный автор диаграмм: пишет DSL-код, использует AI, сохраняет и версионирует диаграммы, экспортирует результат. С Волны 2 может быть владельцем или соавтором диаграммы (см. §5, п. 1) — раздельной роли «администратор» система не вводит, многопользовательское администрирование не требуется. |
| **AI-провайдер** | Внешняя система (LLM/VLM) или `StubAIProvider`, вызываемая через единый интерфейс `AIProvider` (`backend/app/domain/interfaces.py`). Не актор с точки зрения UI, но участвует в сценариях FR-AI-*. |
| **Внешнее хранилище** | GitHub API, Google Drive API — через `StorageProvider` (`backend/app/domain/interfaces.py`); реализовано пока только `LocalDownloadProvider`. |

## 4. Глоссарий

| Термин | Значение |
|---|---|
| DSL | Собственный текстовый язык описания диаграмм проекта (грамматика — `backend/app/dsl/grammar.lark`). |
| Нотация (notation) | Плагин из реестра `app/notations`, определяющий допустимые виды узлов/связей, валидацию и рендер (напр. `erd.crows_foot.logical`). |
| Профиль нотации | Реализация протокола `NotationProfile`. |
| Commit / Blob | Единицы git-подобного версионирования диаграммы (`backend/app/models/version.py`) — блоб хранит текст DSL и дедуплицируется по SHA-256. |
| Волна | Этап реализации реестра нотаций, см. §5 `00-system-architecture.md`. |
| Режим AI | Один из четырёх режимов ассистента: «Написать код» (`write`), «Исправить код» (`fix_code`), «Исправить ошибку» (`fix_error`), «Документация» (`docs`). |

## 5. Решённые вопросы (закрыты Ксенией)

Ранее здесь был список из шести открытых вопросов. Все шесть заданы напрямую и закрыты
2026-09-17 — ниже итоговые решения. Соответствующие FR/NFR обновлены: пометка
`(допущение, см. 00-overview.md §5, п. N)` заменена на `(решено, см. §5, п. N)`.

1. **Совместный доступ к диаграммам — решено: совместное редактирование.** Диаграмма
   получает роли участников (владелец/соавтор), а не остаётся строго приватной за одним
   `user_id`. Это самое трудоёмкое из шести решений — требует модели ролей доступа
   (`DiagramCollaborator` или аналог), проверки прав на каждый эндпоинт `diagram_service`,
   и, для реалтайм-совместного редактирования, WebSocket-канала синхронизации изменений —
   такой канал уже заложен архитектурно (см. §6 `00-system-architecture.md`, WebSocket
   pub/sub), но сама модель прав и merge-стратегия одновременных правок ещё не
   реализованы в коде. Планируется на Волну 2, после MVP с одним владельцем.
2. **Иерархическая декомпозиция IDEF0/DFD — решено: отдельная связанная `Diagram`-запись.**
   Подтверждена схема родитель/потомок + ссылка на декомпозируемый узел (по аналогии с
   git submodule), как и предполагалось допущением. Требуется добавить в модель `Diagram`
   поля `parent_diagram_id` и `decomposed_node_id` перед началом Волны 2 (`idef3`, `dfd`).
3. **OAuth на экране логина vs OAuth для хранилища — решено: два независимых механизма.**
   Подтверждено: FR-AUTH-04 (вход через OAuth) и FR-STORE-02/03 (авторизация доступа к
   хранилищу) — раздельные сценарии с разным набором прав (scope), связанные только общим
   OAuth-провайдером.
4. **Формат «экспорт в формат нотации» — решено: PlantUML/Mermaid-текст, BPMN 2.0 XML,
   drawio-XML.** Помимо базового экспорта в `.dsl` + SVG + PNG, MVP+ должен уметь
   экспортировать диаграмму в эти три нативных формата (не GraphML — он не запрошен).
   Реализация — отдельный `ExportProvider` на нотацию/формат, Волна 2+.
5. **Численные квоты AI/rate-limit — решено: 20 запросов/день на пользователя.**
   Значение по умолчанию для Redis token/leaky bucket механизма (§6 архитектуры);
   задаётся через конфигурацию (`AI_DAILY_QUOTA` в `.env`), не жёстко в коде.
6. **Мультиязычность интерфейса — решено: настоящий переключатель языка.** Элемент
   «Русский» в статус-баре — не индикатор, а рабочий переключатель, требующий полноценной
   i18n-инфраструктуры (минимум русский + английский). Это меняет NFR: интерфейс больше не
   ограничен одним языком в MVP, локализация становится реальным требованием, а не
   отложенной возможностью — учтено в `02-nonfunctional-requirements.md`.

Пункты 1 и 6 — самые трудоёмкие решения из шести (модель прав доступа + realtime-синхронизация;
полноценная i18n) и требуют дополнительной архитектурной проработки перед реализацией, а не
только правки FR-документов. Остальные четыре (2–5) — точечные, укладываются в существующую
архитектуру без структурных изменений.
