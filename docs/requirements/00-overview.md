# Требования к системе DiagramCode — обзор и правила чтения

**Статус:** актуально
**Связанные документы:** [`docs/architecture/00-system-architecture.md`](../architecture/00-system-architecture.md), [`docs/architecture/01-ai-provider-setup.md`](../architecture/01-ai-provider-setup.md), [`docs/labs/00-labs-mapping.md`](../labs/00-labs-mapping.md)

Этот документ и два соседних (`01-functional-requirements.md`, `02-nonfunctional-requirements.md`) фиксируют требования к DiagramCode так, как они уже вытекают из принятых архитектурных решений, макетов интерфейса (`design/mockups/*.dc.html`) и фактического кода (`backend/app/`). Здесь **не изобретаются новые решения** — документ систематизирует то, что уже согласовано, и явно помечает те немногие места, где решения ещё не принято (раздел «Открытые вопросы» ниже).

---

## 1. Два среза требований

Как и в архитектуре (см. §1 `00-system-architecture.md`), требования существуют в двух срезах:

- **Целевые требования** — полный охват: все нотации (UML, ERD, IDEF0/1X/3, DFD, после MVP — BPMN и сети Петри), AI, все три способа хранения, полная валидация. Помечены волной реализации (Волна 1–4).
- **Курсовой срез** — подмножество, достаточное для защиты курсовой работы (3 обязательных модуля РПЗ за ~30 часов): DSL-редактор + рендер + сохранение + одна нотация (`erd.crows_foot.logical`) с валидацией + аутентификация. Это Волна 1.

Каждое функциональное требование (FR) в `01-functional-requirements.md` помечено тегом волны:

| Тег | Значение | Ссылка на архитектуру |
|---|---|---|
| `[Волна 1 / MVP]` | Курсовой срез — уже частично реализовано в `backend/app/` | §5, "Волна 1" |
| `[Волна 2]` | Следующие нотации и режимы после защиты | §5, "Волна 2" |
| `[Волна 3]` | Полное покрытие UML/ERD/IDEF | §5, "Волна 3" |
| `[Волна 4 / после MVP]` | BPMN и сети Петри | §5, "Волна 4" |

Нефункциональные требования (NFR) волной не помечаются — они действуют на систему в целом с самого начала (даже если конкретный NFR полностью проверяем только после реализации соответствующей волны FR).

## 2. Источники требований

Каждое требование в этих документах опирается на один или несколько источников:

1. **Архитектурные решения** — `docs/architecture/00-system-architecture.md`, `01-ai-provider-setup.md`.
2. **Макеты интерфейса** — 13 файлов в `design/mockups/*.dc.html`: `IDE-Dark`, `IDE-Light`, `Login`, `AIImageUpload`, `AIModalText`, `AIResultBPMN`, `DiffView`, `DocumentationModal`, `PanelResize`, `SaveDropdown`, `SidebarDetail`, `Validation`, `VersionHistory`. Эти макеты — не просто иллюстрации: они содержат конкретные детали поведения (список статусов в статус-баре, состав дропдауна сохранения, вкладки AI-модалки, структура таблицы истории версий и т.д.), которые нигде больше текстом не зафиксированы — поэтому FR по UI прямо ссылаются на конкретный файл макета.
3. **Существующий код** — `backend/app/` (домен, DSL-парсер, нотация ERD, репозитории, сервисы, роуты) и `backend/tests/` — фиксирует уже работающее поведение как требование (не наоборот).
4. **Официальная методичка ИТиВП** (`Часть 2/Курсовое проектирование/03. Структура пояснительной записки к курсовой работе.pdf`) — формат «Пользователь может…» для FR и раздел NFR (производительность/безопасность/адаптивность) заимствован оттуда для совместимости с шаблоном РПЗ.

## 3. Действующие лица (акторы)

| Актор | Описание |
|---|---|
| **Пользователь** | Зарегистрированный автор диаграмм: пишет DSL-код, использует AI, сохраняет и версионирует диаграммы, экспортирует результат. Единственная роль в MVP — разделения на «обычного пользователя» и «администратора» из шаблона РПЗ система не вводит, так как многопользовательского администрирования не требуется (см. открытый вопрос №1). |
| **AI-провайдер** | Внешняя система (LLM/VLM) или `StubAIProvider`, вызываемая через единый интерфейс `AIProvider` (`backend/app/domain/interfaces.py`). Не актор с точки зрения UI, но участвует в сценариях FR-AI-*. |
| **Внешнее хранилище** | GitHub API, Google Drive API — через `StorageProvider` (`backend/app/domain/interfaces.py`); реализовано пока только `LocalDownloadProvider`. |

## 4. Глоссарий

| Термин | Значение |
|---|---|
| DSL | Собственный текстовый язык описания диаграмм проекта (грамматика — `backend/app/dsl/grammar.lark`). |
| Нотация (notation) | Плагин из реестра `app/notations`, определяющий допустимые виды узлов/связей, валидацию и рендер (напр. `erd.crows_foot.logical`). |
| Профиль нотации | Реализация протокола `NotationProfile`. |
| Commit / Blob | Единицы git-подобного версионирования диаграммы (`backend/app/models/version.py`) — блоб хранит текст DSL и дедуплицируется по SHA-256. |
| Волна | Этап реализации реестра нотаций, см. §5 `00-system-architecture.md`. |
| Режим AI | Один из четырёх режимов ассистента: «Написать код» (`write`), «Исправить код» (`fix_code`), «Исправить ошибку» (`fix_error`), «Документация» (`docs`). |

## 5. Открытые вопросы

Ниже — вопросы, которые **не закрыты** ни архитектурным документом, ни макетами, ни кодом, и по которым требуется решение Ксении, прежде чем соответствующие FR можно считать окончательными. По каждому ниже указано временное допущение, заложенное в FR/NFR документах, чтобы работа не блокировалась.

1. **Совместный доступ к диаграммам.** Ни в архитектуре, ни в макетах нет упоминания шаринга диаграммы другим пользователям (публичная ссылка, совместное редактирование, роль «читатель»/«соавтор»). Модель `Diagram.user_id` — один явный владелец. **Допущение в FR:** MVP и все волны — диаграммы приватны, видны только владельцу; шаринг явно вне текущего скоупа.
2. **Иерархическая декомпозиция для IDEF0/DFD.** IDEF0 требует пары «контекстная диаграмма + декомпозиция», DFD — многоуровневую декомпозицию (см. §5 архитектуры, Волна 2–3). Ни модель `Diagram`, ни грамматика `grammar.lark` не описывают связь «диаграмма верхнего уровня → диаграмма-декомпозиция конкретного узла». **Допущение в FR:** декомпозиция моделируется как отдельная связанная `Diagram`-запись (родитель/потомок + ссылка на декомпозируемый узел), по аналогии с git submodule — но это архитектурное решение, а не факт из существующего кода, и его нужно подтвердить или изменить до начала Волны 2 (`idef3`, `dfd`) и Волны 3 (`idef1x`, полный `idef0`).
3. **OAuth на экране логина vs OAuth для хранилища.** `Login.dc.html` показывает кнопки «GitHub»/«Google» на экране входа в аккаунт, а `SaveDropdown.dc.html` — отдельно кнопки «GitHub (API commit)» / «Google Drive (API upload)» для сохранения. Сейчас в коде реализована только аутентификация по email/паролю (`backend/app/services/auth_service.py`) — OAuth не реализован ни для входа, ни для хранилища. Неясно: это один и тот же OAuth-грант (вход через GitHub одновременно даёт право коммитить в репозиторий) или два независимых сценария с разными scope. **Допущение в FR:** это два независимых механизма (FR-AUTH-04 — вход через OAuth как альтернатива паролю; FR-STORE-02/03 — отдельная авторизация доступа к хранилищу при первом сохранении), связанные только тем, что пользуются одним и тем же OAuth-провайдером.
4. **Формат «экспорт в формат нотации».** Помимо SVG/PNG упоминается экспорт «в формат нотации» — неясно, какие именно нативные форматы имеются в виду (PlantUML/Mermaid/DOT-текст, BPMN 2.0 XML, GraphML, drawio-XML). В библиографии (`docs/literature/bibliography.md`, пп. 99–104) эти инструменты упомянуты как источники вдохновения для layout-движка, а не как обязательные экспорт-цели. **Допущение в FR:** MVP экспортирует исходный DSL-текст (`.dsl`) + SVG + PNG; экспорт в сторонние нотационные форматы (BPMN XML и т.п.) — отдельная возможность Волны 4, требующая отдельного уточнения, какие именно форматы нужны.
5. **Численные квоты AI/rate-limit.** Архитектура называет Redis token/leaky bucket механизм для защиты бесплатной квоты AI-провайдера (§6 архитектуры, `bibliography.md` п. 70), но не называет конкретных чисел (запросов в минуту/день на пользователя). **Допущение в NFR:** лимит задаётся через конфигурацию (`.env`), а не жёстко в коде; конкретное значение по умолчанию нужно будет откалибровать под реальный бесплатный тариф выбранного AI-провайдера (Gemini/OpenRouter, см. `01-ai-provider-setup.md`) при его подключении.
6. **Мультиязычность интерфейса.** Статус-бар в макетах (`IDE-Dark.dc.html`, `IDE-Light.dc.html`) показывает элемент «Русский» рядом с индикаторами кодировки/языка файла. Неясно, это переключатель языка интерфейса (i18n на 2+ языка) или просто индикатор языка проверки правописания/раскладки. **Допущение в NFR:** интерфейс на MVP — только русский язык; элемент статус-бара — индикатор (не функционирующий переключатель); полноценная локализация — вне скоупа, пока не запрошена явно.

Эти шесть пунктов не блокируют написание FR/NFR ниже — они снабжены допущениями и явно помечены в соответствующих требованиях как `(допущение, см. 00-overview.md §5, п. N)`.
