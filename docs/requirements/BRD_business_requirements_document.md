# Business Requirements Document (BRD) — DiagramCode

**Статус:** актуально
**Связанные документы:** `business_requirements.md`, `user_requirements.md`, `00-overview.md`

## 1. Назначение документа

Документ фиксирует, зачем существует проект DiagramCode и что именно должно получиться в результате — на уровне бизнес-целей, а не технической реализации (техническая часть — в `01-functional-requirements.md`/`02-nonfunctional-requirements.md`).

## 2. Бизнес-контекст и обоснование (Business Case)

Проект одновременно решает две реальные задачи одним и тем же кодом:

1. **Учебная задача** — выполнение курсового проекта и лабораторных работ по дисциплине «Интернет-технологии и веб-программирование» (обе части, БГУИР), с полным набором артефактов, ожидаемых учебной программой: рабочий backend/frontend, версионирование, требования, тестирование.
2. **Продуктовая задача** — построение реально работающего сервиса «diagram as code» (аналог PlantUML/Mermaid/Eraser.io, см. `06_market_and_extras/00-competitive-analysis.md`), который можно показать как портфолио-проект: реальный, а не учебный по глубине проработки.

Обе задачи выполняются одной кодовой базой намеренно — учебные требования и продуктовые не противоречат друг другу, а курсовой срез (Волна 1) является честным подмножеством целевой системы.

## 3. Бизнес-цели (Business Objectives)

| ID | Цель | Как измерить успех |
|---|---|---|
| BO-01 | Успешно защитить лабораторные работы и курсовой проект по обеим частям дисциплины | Все лабы 1–8 обеих частей сданы и приняты, курсовой проект защищён |
| BO-02 | Получить работающий продукт, пригодный для демонстрации (портфолио) | Пользователь может зарегистрироваться, написать DSL-код, увидеть рендер, сохранить версию — end-to-end, без макетов |
| BO-03 | Архитектура должна быть расширяемой, а не одноразовой | Добавление новой нотации не требует переписывания ядра (см. NFR-MAINT-01, уже подтверждено 4 реализованными нотациями) |
| BO-04 | Не создавать риска на защите из-за нечестных/сфабрикованных артефактов | Все скриншоты и данные в отчётах — реальные или явно помечены как заменители (см. `feedback_academic_integrity` — принцип честности скриншотов) |

## 4. Область применения (Scope)

**Входит в область:**
- Веб-сервис редактирования диаграмм через собственный DSL с версионированием, AI-генерацией, экспортом.
- Полный цикл разработки: требования → архитектура → реализация → тестирование → документация.
- Отдельно — коучерская программа (Часть 2 ИТиВП): Node.js/Express/Sequelize/MongoDB/WebSocket/Docker лабораторные работы на смежном, но архитектурно отдельном стеке (не путать с основным Python/FastAPI продуктом).

**Не входит в область (сознательно, см. `06_market_and_extras/00-post-mvp-features.md` за списком идей вне MVP):**
- Коммерческий запуск, монетизация, реальные пользователи вне учебного контекста.
- Полная реализация всех 4 волн нотаций одновременно — реализуется поэтапно.

## 6. Ограничения и допущения (Constraints & Assumptions)

- Ограничение по времени: курсовой проект — ориентировочно 30 часов согласно методичке (курсовой срез рассчитан под это ограничение, полная система — сверх него).
- Ограничение по инфраструктуре: только бесплатные сервисы, доступные из Беларуси (Render/Supabase/Netlify/Neon — см. `02_architecture_diagrams/00-system-architecture.md`, §7).
- Допущение: у пользователя есть современный браузер; мобильная версия самого IDE не является целью (см. FR-UI-12).

## 7. Критерии приёмки на уровне бизнеса

- Курсовой срез (Волна 1) полностью проходит демонстрацию без сбоев на защите.
- Лабораторные работы Часть 2 (1–8) соответствуют реальному содержанию LMS-курса, а не только названию лабы.
- Ни один артефакт (отчёт, скриншот, диаграмма) не содержит вымышленных данных, выданных за реальные.
