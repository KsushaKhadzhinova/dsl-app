# Варианты использования (use cases)

**Статус:** актуально
**Связанные документы:** [`00-overview.md`](00-overview.md) (акторы, глоссарий), [`01-functional-requirements.md`](01-functional-requirements.md) (FR по каждому UC), [`../architecture/03-sequence-diagrams.md`](../architecture/03-sequence-diagrams.md) (детальные сценарии как диаграммы последовательностей).

Этот документ переводит таблицы FR в форму, привычную для раздела «Постановка задачи» РПЗ и для UML use-case диаграммы: кто, зачем и при каких условиях взаимодействует с системой.

## 1. Акторы

См. `00-overview.md` §3. Кратко:

- **Пользователь** — зарегистрированный автор диаграмм (с Волны 2 — владелец или соавтор).
- **AI-провайдер** — внешняя LLM/VLM-система или `StubAIProvider`, участвует как второстепенный актор в сценариях с AI.
- **Внешнее хранилище** — GitHub API / Google Drive API, второстепенный актор в сценариях экспорта/импорта.

## 3. Детальные сценарии (все 21 UC)

### UC-01. Регистрация в системе

- **Актор:** Пользователь.
- **Предусловие:** пользователь не аутентифицирован; email ранее не зарегистрирован.
- **Основной поток:**
  1. Пользователь открывает `/register` и заполняет email, username, пароль.
  2. Система проверяет формат email и совпадение паролей на клиенте.
  3. Система отправляет `POST /api/v1/auth/register`.
  4. Backend проверяет уникальность email, хеширует пароль (bcrypt), создаёт запись `User`.
  5. Система возвращает JWT и перенаправляет на `/`.
- **Альтернативный поток:** email уже занят → backend возвращает 400 с сообщением, форма показывает ошибку без сброса введённых значений.
- **Постусловие:** создан `User`, пользователь аутентифицирован.
- **Связанные FR:** FR-AUTH-01, FR-AUTH-03.

### UC-02. Вход в систему

- **Актор:** Пользователь (уже зарегистрированный).
- **Предусловие:** учётная запись существует; пользователь не аутентифицирован.
- **Основной поток:**
  1. Пользователь открывает `/login`, вводит email и пароль.
  2. Система отправляет `POST /api/v1/auth/login`.
  3. Backend сверяет bcrypt-хэш пароля, выдаёт JWT (`TokenResponse`).
  4. Клиент сохраняет токен и перенаправляет на `/`.
- **Альтернативный поток:** неверный email или пароль → 401 с единым сообщением, не раскрывающим, что именно неверно (чтобы нельзя было перебором узнать, какие email зарегистрированы).
- **Постусловие:** пользователь аутентифицирован до истечения срока действия токена.
- **Связанные FR:** FR-AUTH-02, FR-AUTH-05.

### UC-03. Вход через OAuth (план, Волна 2)

- **Актор:** Пользователь, OAuth-провайдер (GitHub/Google).
- **Предусловие:** у пользователя есть аккаунт у провайдера; в конфигурации системы заданы `client_id`/`client_secret` (иначе кнопка недоступна).
- **Основной поток:**
  1. Пользователь нажимает кнопку GitHub/Google на `/login`.
  2. Браузер перенаправляется на страницу согласия провайдера.
  3. После согласия провайдер возвращает authorization code на callback-адрес системы.
  4. Backend обменивает code на access token провайдера, получает email пользователя.
  5. Система находит существующего `User` по email или создаёт нового, выдаёт свой JWT (тот же формат, что и UC-02).
- **Альтернативный поток:** пользователь отменяет согласие у провайдера → возврат на `/login` без токена, учётная запись не создаётся.
- **Постусловие:** пользователь аутентифицирован системным JWT так же, как после обычного логина.
- **Связанные FR:** FR-AUTH-04, FR-UI-10. Независимый механизм от OAuth-авторизации внешнего хранилища (UC-13) — см. `00-overview.md` §5, п. 3.
- **Статус:** не реализовано в коде на момент этого документа — заготовка конфигурации (`github_client_id/secret`, `google_oauth_client_id/secret`) есть, сам флоу нет.

### UC-04. Написание и рендер DSL-кода

- **Актор:** Пользователь.
- **Предусловие:** пользователь аутентифицирован, находится в IDE (`/`).
- **Основной поток:**
  1. Пользователь выбирает нотацию в выпадающем списке.
  2. Пользователь пишет/редактирует DSL-код в редакторе Monaco с подсветкой синтаксиса.
  3. Пользователь нажимает **Run** (или срабатывает debounce-автозапуск).
  4. Система парсит код (`dsl/parser.py`), строит `DiagramModel`, валидирует его профилем нотации.
  5. При отсутствии ошибок — рендерит SVG и обновляет канвас; при наличии — заполняет вкладку Problems.
- **Альтернативные потоки:**
  - Синтаксическая ошибка → `DslSyntaxError` с точной позицией → подсветка строки в редакторе (UC-05).
  - Диаграмма большая → рендер уходит в очередь воркеров, результат приходит по WebSocket (FR-REN-04).
- **Постусловие:** канвас отображает актуальный рендер либо список проблем.
- **Связанные FR:** FR-DSL-01…06, FR-REN-01…03, FR-NOT-03, FR-NOT-04.

### UC-05. Просмотр ошибок и предупреждений валидации

- **Актор:** Пользователь.
- **Предусловие:** диаграмма открыта, выполнен хотя бы один Run (см. UC-04).
- **Основной поток:**
  1. Парсер/валидатор возвращает список проблем (`error`/`warning`) с точной строкой и столбцом.
  2. Система заполняет вкладку **Problems** нижней панели этим списком.
  3. Редактор подсвечивает соответствующие строки: `error` — блокирует рендер, `warning` — волнистое подчёркивание и жёлтый фон, ввод не блокируется.
  4. Пользователь кликает на пункт в Problems → курсор редактора переходит на нужную строку/столбец.
- **Альтернативный поток:** список проблем пуст → вкладка Problems не показывает ничего, рендер уже выполнен (см. UC-04).
- **Постусловие:** пользователь точно знает, где и что исправить, не читая общий текст ошибки без контекста.
- **Связанные FR:** FR-NOT-13, FR-NOT-14, FR-DSL-05.

### UC-06. Сохранение версии диаграммы

- **Актор:** Пользователь.
- **Предусловие:** диаграмма открыта, код успешно прошёл хотя бы синтаксический разбор (сохранение с ошибками валидации допустимо — это черновик, а не рендер).
- **Основной поток:**
  1. Пользователь нажимает **Save**, опционально указывает комментарий к версии.
  2. Система вычисляет SHA-256 текста DSL.
  3. Если Blob с таким хэшем уже существует — переиспользуется; иначе создаётся новый.
  4. Создаётся `Commit`, ссылающийся на `Blob`, с автором `user` и меткой времени.
- **Постусловие:** в истории версий диаграммы появляется новая запись.
- **Связанные FR:** FR-VER-01…04, FR-VER-07.

### UC-07. Просмотр истории версий и откат (Волна 2)

- **Актор:** Пользователь.
- **Предусловие:** у диаграммы есть минимум две сохранённые версии.
- **Основной поток:**
  1. Пользователь открывает окно истории версий — таблица версий (номер, автор `user`/`ai`, комментарий, время, число узлов/связей).
  2. Выбирает две версии и запрашивает построчный diff — система строит его по алгоритму Myers (O(ND)), показывает добавленные/удалённые строки side-by-side и миниатюру канваса новой версии.
- **Альтернативный поток:** вместо diff пользователь нажимает **Откатиться** на конкретной версии → система создаёт новый commit с содержимым выбранной старой версии (аналог `git revert`, история не теряется — в отличие от `git reset --hard`).
- **Постусловие:** либо показан diff между версиями, либо в истории появился новый commit с восстановленным содержимым.
- **Связанные FR:** FR-VER-05, FR-VER-06, FR-VER-08, FR-UI-07.

### UC-08. Генерация DSL-кода через AI

- **Актор:** Пользователь, AI-провайдер.
- **Предусловие:** пользователь аутентифицирован; дневная AI-квота не исчерпана.
- **Основной поток:**
  1. Пользователь открывает модальное окно AI, выбирает режим «Написать код», указывает нотацию и текстовое описание.
  2. Система проверяет rate-limit (Redis token/leaky bucket, `AI_DAILY_QUOTA`).
  3. Запрос уходит выбранному `AIProvider` (реальному или `StubAIProvider`, если ключ не сконфигурирован).
  4. Система получает DSL-код, вставляет его в редактор с атрибуцией «AI ✦ …», немедленно рендерит.
  5. Запрос логируется в `AIRequest` (режим, промпт, результат, время) — отдельно от истории версий.
- **Альтернативный поток:** квота исчерпана → система отклоняет запрос с понятным сообщением («Дневной лимit AI-запросов исчерпан»), не обращаясь к провайдеру.
- **Постусловие:** редактор содержит сгенерированный код; создана запись `AIRequest`.
- **Связанные FR:** FR-AI-01…03, FR-AI-08…12.

### UC-09. Исправление кода/ошибки через AI

- **Актор:** Пользователь, AI-провайдер.
- **Предусловие:** пользователь аутентифицирован, дневная AI-квота не исчерпана.
- **Основной поток (режим «Исправить ошибку»):**
  1. Во вкладке Problems рядом с конкретной ошибкой пользователь нажимает «Исправить через AI».
  2. Система автоматически передаёт `AIProvider.fix_dsl` текущий код и текст последней ошибки валидации/парсинга — без необходимости переформулировать проблему текстом.
  3. Получает предложенный исправленный код, показывает его как предложение (diff-превью), а не заменяет молча.
  4. Пользователь принимает или отклоняет предложение.
- **Альтернативный поток (режим «Исправить код»):** пользователь сам открывает AI-модалку и выбирает «Исправить код» для кода без явной ошибки (рефакторинг/улучшение), минуя автоматическую передачу текста ошибки.
- **Постусловие:** при принятии — редактор обновлён; в любом случае создана запись `AIRequest`.
- **Связанные FR:** FR-AI-04, FR-AI-05, FR-AI-08, FR-AI-11.

### UC-10. Распознавание диаграммы по изображению (image→DSL)

- **Актор:** Пользователь, AI-провайдер (VLM).
- **Предусловие:** пользователь аутентифицирован, квота не исчерпана; есть файл изображения диаграммы.
- **Основной поток:**
  1. Пользователь открывает AI-модалку, перетаскивает (drag-and-drop) или выбирает файл PNG/SVG/JPG (до 10 МБ).
  2. Система передаёт изображение `AIProvider` для распознавания фигур, текста и связей.
  3. Получает предложенный DSL-код, вставляет его в редактор с атрибуцией «AI ✦ …», немедленно рендерит для проверки.
- **Альтернативный поток:** файл превышает 10 МБ или имеет неподдерживаемый формат → отклоняется на клиенте до отправки запроса, с понятным сообщением.
- **Постусловие:** в редакторе — черновик DSL, полученный из изображения; пользователь правит его как обычный код.
- **Связанные FR:** FR-AI-07, FR-AI-08.

### UC-11. Получение справки от AI-ассистента, режим «Документация» (Волна 2)

- **Актор:** Пользователь, AI-провайдер.
- **Предусловие:** пользователь аутентифицирован.
- **Основной поток:**
  1. Открывает AI-модалку, выбирает режим «Документация».
  2. Задаёт вопрос о синтаксисе DSL или конкретной нотации.
  3. Система передаёт вопрос AI вместе с содержимым встроенной документации как контекстом.
  4. Показывает текстовый ответ в модалке.
- **Альтернативный поток:** нет отдельного отказа по теме вопроса — это режим справки, а не генерации кода; ответ ограничен доступным контекстом документации.
- **Постусловие:** пользователь получил текстовый ответ; ни код диаграммы, ни история версий не изменяются (в отличие от UC-08/UC-09).
- **Связанные FR:** FR-AI-06.

### UC-12. Экспорт диаграммы (на устройство / SVG / PNG)

- **Актор:** Пользователь.
- **Предусловие:** для `.dsl` — диаграмма существует; для SVG/PNG — диаграмма отрендерена без ошибок.
- **Основной поток:**
  1. Пользователь открывает выпадающий список **Save ▾**, выбирает «На устройство».
  2. Выбирает формат: исходный `.dsl`, SVG или PNG текущего рендера.
  3. Браузер формирует Blob и скачивает файл через `<a download>`.
- **Альтернативный поток:** диаграмма не отрендерена или содержит блокирующие ошибки → пункты SVG/PNG недоступны, доступен только `.dsl`.
- **Постусловие:** файл сохранён в файловой системе пользователя.
- **Связанные FR:** FR-STORE-01, FR-STORE-04, FR-STORE-05.

### UC-13. Сохранение в GitHub / Google Drive (Волна 2)

- **Актор:** Пользователь, Внешнее хранилище (GitHub API / Google Drive API).
- **Предусловие:** пользователь авторизовал OAuth-доступ к соответствующему хранилищу — независимый механизм от входа в саму систему (UC-02/UC-03).
- **Основной поток:**
  1. Пользователь выбирает **Save ▾** → GitHub (или Google Drive).
  2. Система использует OAuth-токен хранилища, выполняет коммит файла в репозиторий (или загрузку в Drive) через соответствующий API.
  3. Показывает тост об успехе со ссылкой на результат.
- **Альтернативный поток:** OAuth-доступ к хранилищу не выдан или истёк → система заново инициирует OAuth-флоу перед сохранением.
- **Постусловие:** файл диаграммы появляется во внешнем хранилище пользователя.
- **Связанные FR:** FR-STORE-02, FR-STORE-03.
- **Статус:** не реализовано — есть только заготовка конфигурации клиента; требует решения пользователя об OAuth-регистрации (см. `docs/setup/02-manual-tasks-for-ksenia.md`).

### UC-14. Экспорт в нативный формат (PlantUML/Mermaid/BPMN XML/drawio) (Волна 4)

- **Актор:** Пользователь.
- **Предусловие:** диаграмма отрендерена без ошибок; выбранный формат применим к текущей нотации (например, BPMN XML — только для нотаций семейства `bpmn.*`).
- **Основной поток:**
  1. Пользователь выбирает **Save ▾** → «На устройство» → один из нативных форматов вместо `.dsl`/SVG/PNG.
  2. Система транслирует `DiagramModel` в целевой текстовый формат.
  3. Браузер скачивает результирующий файл.
- **Альтернативный поток:** формат не применим к текущей нотации → пункт не показан в списке.
- **Постусловие:** файл в стороннем формате пригоден для открытия в соответствующем внешнем инструменте (draw.io, PlantUML-рендерер и т.п.).
- **Связанные FR:** FR-STORE-06.

### UC-15. Импорт существующего `.dsl`-файла

- **Актор:** Пользователь.
- **Предусловие:** у пользователя есть локальный `.dsl`-файл.
- **Основной поток:**
  1. Пользователь нажимает **Import**, выбирает файл через системный диалог.
  2. Система читает содержимое как текст и подставляет в редактор.
  3. Если текущий код не сохранён — запрашивает подтверждение перед заменой.
  4. Пользователь может сразу нажать Run (см. UC-04).
- **Альтернативный поток:** файл не `.dsl`, повреждён или не текстовый → отклоняется с понятным сообщением, содержимое редактора не меняется.
- **Постусловие:** редактор содержит импортированный код.
- **Связанные FR:** FR-STORE-07.

### UC-16. Совместное редактирование диаграммы

- **Актор:** несколько пользователей одновременно (владелец + соавтор(ы)).
- **Предусловие:** владелец добавил соавтора по email/username; оба пользователя открыли одну и ту же диаграмму.
- **Основной поток:**
  1. Владелец диаграммы отправляет запрос на добавление соавтора.
  2. Система создаёт запись `DiagramCollaborator` (роль: editor/viewer).
  3. Оба клиента открывают WebSocket-канал, привязанный к `diagram_id`.
  4. Изменения одного клиента транслируются другому через pub/sub-канал в реальном времени.
- **Постусловие:** оба пользователя видят согласованное состояние диаграммы.
- **Связанные FR:** FR-AUTH-08. Требует модель прав доступа и merge-стратегию одновременных правок (см. `00-overview.md` §5, п. 1 — самое трудоёмкое из решённых расширений, запланировано на Волну 2).

### UC-17. Декомпозиция узла (IDEF0/DFD)

- **Актор:** Пользователь.
- **Предусловие:** открыта диаграмма нотации IDEF0 или DFD, есть узел без дочерней декомпозиции.
- **Основной поток:**
  1. Пользователь выбирает узел и вызывает действие «Декомпозировать».
  2. Система создаёт новую `Diagram` с `parent_diagram_id` = текущая диаграмма и `decomposed_node_id` = выбранный узел.
  3. Пользователь описывает декомпозицию в новой, отдельной диаграмме (по аналогии с git submodule).
- **Постусловие:** родительский узел помечен как декомпозированный, ссылается на дочернюю диаграмму.
- **Связанные FR:** FR-NOT-06a, FR-NOT-11 (ICOM-полнота для IDEF0).

### UC-18. Переключение темы интерфейса

- **Актор:** Пользователь.
- **Предусловие:** —
- **Основной поток:**
  1. Пользователь нажимает кнопку темы в титлбаре.
  2. Интерфейс мгновенно переключается на второй самостоятельный набор цветовых переменных (фон/текст/акценты/подсветка синтаксиса) — не инверсию цветов первого.
  3. Если пользователь аутентифицирован, выбор сохраняется в `User.theme_preference`.
- **Альтернативный поток:** пользователь не аутентифицирован → тема хранится только на время сессии браузера, без сохранения в профиль.
- **Постусловие:** тема применена; при следующем входе аутентифицированного пользователя восстанавливается сохранённая тема.
- **Связанные FR:** FR-UI-05, FR-AUTH-07.

### UC-19. Переключение языка интерфейса

- **Актор:** Пользователь.
- **Предусловие:** —
- **Основной поток:**
  1. Пользователь выбирает язык (русский/английский) в статус-баре или настройках.
  2. Интерфейс перерисовывается с текстами выбранного языка без перезагрузки страницы.
- **Постусловие:** интерфейс отображается на выбранном языке.
- **Связанные FR:** NFR-A11Y-04.

### UC-20. Изменение размеров панелей IDE

- **Актор:** Пользователь.
- **Предусловие:** IDE открыта.
- **Основной поток:**
  1. Пользователь наводит курсор на границу панелей (editor↔canvas, sidebar↔editor, высота нижней панели) — курсор меняется на resize-иконку.
  2. Перетаскивает границу мышью — панели меняют размер в реальном времени.
- **Альтернативный поток (Волна 2):** двойной клик по ручке границы → панель возвращается к размеру по умолчанию; итоговые пропорции сохраняются в настройках проекта между сессиями.
- **Постусловие:** размеры панелей соответствуют выбору пользователя.
- **Связанные FR:** FR-UI-02, FR-UI-03.

### UC-21. Использование шаблонов диаграмм

- **Актор:** Пользователь.
- **Предусловие:** открыта панель шаблонов в сайдбаре.
- **Основной поток:**
  1. Пользователь ищет шаблон по названию нотации в поле поиска шаблонов.
  2. Выбирает шаблон из списка результатов.
  3. Нажимает «Вставить шаблон» — готовый DSL-код шаблона появляется в редакторе (с подтверждением, если текущий код не пуст и не сохранён).
- **Альтернативный поток:** поиск не даёт совпадений → список пуст, явно показано «ничего не найдено».
- **Постусловие:** редактор содержит код шаблона, готовый к правке или сразу к Run (UC-04).
- **Связанные FR:** FR-DSL-09, FR-DSL-10.
