# Варианты использования (use cases)

**Статус:** актуально
**Связанные документы:** [`00-overview.md`](00-overview.md) (акторы, глоссарий), [`01-functional-requirements.md`](01-functional-requirements.md) (FR по каждому UC), [`../architecture/03-sequence-diagrams.md`](../architecture/03-sequence-diagrams.md) (детальные сценарии как диаграммы последовательностей).

Этот документ переводит таблицы FR в форму, привычную для раздела «Постановка задачи» РПЗ и для UML use-case диаграммы: кто, зачем и при каких условиях взаимодействует с системой.

---

## 1. Акторы

См. `00-overview.md` §3. Кратко:

- **Пользователь** — зарегистрированный автор диаграмм (с Волны 2 — владелец или соавтор).
- **AI-провайдер** — внешняя LLM/VLM-система или `StubAIProvider`, участвует как второстепенный актор в сценариях с AI.
- **Внешнее хранилище** — GitHub API / Google Drive API, второстепенный актор в сценариях экспорта/импорта.

## 3. Детальные сценарии (основные UC)

### UC-01. Регистрация в системе

- **Актор:** Пользователь.
- **Предусловие:** пользователь не аутентифицирован; email ранее не зарегистрирован.
- **Основной поток:**
  1. Пользователь открывает `/register` и заполняет email, username, пароль.
  2. Система проверяет формат email и совпадение паролей на клиенте.
  3. Система отправляет `POST /api/v1/auth/register`.
  4. Backend проверяет уникальность email, хеширует пароль (bcrypt), создаёт запись `User`.
  5. Система возвращает JWT и перенаправляет на `/`.
- **Альтернативный поток:** email уже занят → backend возвращает 400 с сообщением, форма показывает ошибку без сброса введённых значений.
- **Постусловие:** создан `User`, пользователь аутентифицирован.
- **Связанные FR:** FR-AUTH-01, FR-AUTH-03.

### UC-04. Написание и рендер DSL-кода

- **Актор:** Пользователь.
- **Предусловие:** пользователь аутентифицирован, находится в IDE (`/`).
- **Основной поток:**
  1. Пользователь выбирает нотацию в выпадающем списке.
  2. Пользователь пишет/редактирует DSL-код в редакторе Monaco с подсветкой синтаксиса.
  3. Пользователь нажимает **Run** (или срабатывает debounce-автозапуск).
  4. Система парсит код (`dsl/parser.py`), строит `DiagramModel`, валидирует его профилем нотации.
  5. При отсутствии ошибок — рендерит SVG и обновляет канвас; при наличии — заполняет вкладку Problems.
- **Альтернативные потоки:**
  - Синтаксическая ошибка → `DslSyntaxError` с точной позицией → подсветка строки в редакторе (UC-05).
  - Диаграмма большая → рендер уходит в очередь воркеров, результат приходит по WebSocket (FR-REN-04).
- **Постусловие:** канвас отображает актуальный рендер либо список проблем.
- **Связанные FR:** FR-DSL-01…06, FR-REN-01…03, FR-NOT-03, FR-NOT-04.

### UC-06. Сохранение версии диаграммы

- **Актор:** Пользователь.
- **Предусловие:** диаграмма открыта, код успешно прошёл хотя бы синтаксический разбор (сохранение с ошибками валидации допустимо — это черновик, а не рендер).
- **Основной поток:**
  1. Пользователь нажимает **Save**, опционально указывает комментарий к версии.
  2. Система вычисляет SHA-256 текста DSL.
  3. Если Blob с таким хэшем уже существует — переиспользуется; иначе создаётся новый.
  4. Создаётся `Commit`, ссылающийся на `Blob`, с автором `user` и меткой времени.
- **Постусловие:** в истории версий диаграммы появляется новая запись.
- **Связанные FR:** FR-VER-01…04, FR-VER-07.

### UC-08. Генерация DSL-кода через AI

- **Актор:** Пользователь, AI-провайдер.
- **Предусловие:** пользователь аутентифицирован; дневная AI-квота не исчерпана.
- **Основной поток:**
  1. Пользователь открывает модальное окно AI, выбирает режим «Написать код», указывает нотацию и текстовое описание.
  2. Система проверяет rate-limit (Redis token/leaky bucket, `AI_DAILY_QUOTA`).
  3. Запрос уходит выбранному `AIProvider` (реальному или `StubAIProvider`, если ключ не сконфигурирован).
  4. Система получает DSL-код, вставляет его в редактор с атрибуцией «AI ✦ …», немедленно рендерит.
  5. Запрос логируется в `AIRequest` (режим, промпт, результат, время) — отдельно от истории версий.
- **Альтернативный поток:** квота исчерпана → система отклоняет запрос с понятным сообщением («Дневной лимit AI-запросов исчерпан»), не обращаясь к провайдеру.
- **Постусловие:** редактор содержит сгенерированный код; создана запись `AIRequest`.
- **Связанные FR:** FR-AI-01…03, FR-AI-08…12.

### UC-16. Совместное редактирование диаграммы

- **Актор:** несколько пользователей одновременно (владелец + соавтор(ы)).
- **Предусловие:** владелец добавил соавтора по email/username; оба пользователя открыли одну и ту же диаграмму.
- **Основной поток:**
  1. Владелец диаграммы отправляет запрос на добавление соавтора.
  2. Система создаёт запись `DiagramCollaborator` (роль: editor/viewer).
  3. Оба клиента открывают WebSocket-канал, привязанный к `diagram_id`.
  4. Изменения одного клиента транслируются другому через pub/sub-канал в реальном времени.
- **Постусловие:** оба пользователя видят согласованное состояние диаграммы.
- **Связанные FR:** FR-AUTH-08. Требует модель прав доступа и merge-стратегию одновременных правок (см. `00-overview.md` §5, п. 1 — самое трудоёмкое из решённых расширений, запланировано на Волну 2).

### UC-17. Декомпозиция узла (IDEF0/DFD)

- **Актор:** Пользователь.
- **Предусловие:** открыта диаграмма нотации IDEF0 или DFD, есть узел без дочерней декомпозиции.
- **Основной поток:**
  1. Пользователь выбирает узел и вызывает действие «Декомпозировать».
  2. Система создаёт новую `Diagram` с `parent_diagram_id` = текущая диаграмма и `decomposed_node_id` = выбранный узел.
  3. Пользователь описывает декомпозицию в новой, отдельной диаграмме (по аналогии с git submodule).
- **Постусловие:** родительский узел помечен как декомпозированный, ссылается на дочернюю диаграмму.
- **Связанные FR:** FR-NOT-06a, FR-NOT-11 (ICOM-полнота для IDEF0).
