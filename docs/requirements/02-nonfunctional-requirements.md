# Нефункциональные требования (NFR)

**Статус:** актуально
**Правила чтения:** см. [`00-overview.md`](00-overview.md). В отличие от FR, требования здесь не привязаны к волне реализации нотаций — они описывают качества системы в целом с самого начала.

---

## 1. Производительность

| ID | Требование | Источник |
|---|---|---|
| NFR-PERF-01 | Рендер типичной учебной диаграммы (десятки узлов) должен укладываться в единицы–десятки миллисекунд на воркере — как в примере в макете (`48ms` для сети Петри из 4 мест/2 переходов). | `design/mockups/IDE-Dark.dc.html` (`bp-body`, «48ms») |
| NFR-PERF-02 | CPU-затратные операции (парсинг+рендер больших диаграмм, вызовы AI) не должны выполняться в процессе, обслуживающем HTTP-запросы: они выносятся в очередь задач (Redis + RQ), выполняются в отдельном воркер-пуле. | архитектура §3, `backend/app/worker/tasks.py` |
| NFR-PERF-03 | Одинаковый DSL-код + одна и та же нотация не должны пересчитываться повторно: результат рендера кэшируется в Redis по хэшу входа. | архитектура §6 |
| NFR-PERF-04 | Автообновление канваса при наборе кода должно использовать debounce (задержку после паузы ввода), чтобы не запускать рендер на каждое нажатие клавиши. | `bibliography.md` п. 95 |
| NFR-PERF-05 | Формальный анализ сетей Петри (граф достижимости) ограничивается bounded-сетями разумного размера по фундаментальной вычислительной причине (EXPSPACE-полнота задачи достижимости) — это документированное ограничение, а не дефект производительности, который можно устранить оптимизацией. | архитектура §5 |
| NFR-PERF-06 | Frontend должен проходить аудит Google Lighthouse по производительности и доступности с результатом, пригодным для демонстрации на защите курсовой работы (конкретный числовой порог не фиксируется — предмет отдельной калибровки после сборки frontend). | `bibliography.md` пп. 66, 91; методичка, Модуль 06 |

## 2. Безопасность

| ID | Требование | Источник |
|---|---|---|
| NFR-SEC-01 | Пароли пользователей должны храниться только в виде bcrypt-хэша; система не должна логировать или возвращать пароль в открытом виде ни в одном ответе API. | `backend/app/core/security.py` |
| NFR-SEC-02 | Доступ к диаграммам и их версиям должен быть авторизован через JWT и ограничен владельцем ресурса (см. FR-AUTH-05/06). | `backend/app/api/deps.py` |
| NFR-SEC-03 | Секреты (JWT-ключ, AI API-ключ, OAuth client secret) должны конфигурироваться только через переменные окружения (`.env`), никогда не хардкодиться в репозитории; значение по умолчанию для dev-режима явно помечено как небезопасное (`insecure-dev-key-change-me`). | `backend/app/core/config.py::Settings.jwt_secret_key` |
| NFR-SEC-04 | Система должна защищать от инъекции произвольного HTML/SVG при вставке сгенерированного SVG-рендера в DOM React-приложения (санитизация или безопасный способ вставки, исключающий выполнение скриптов из пользовательского DSL). | `bibliography.md` п. 67 (OWASP Top 10, XSS) |
| NFR-SEC-05 | CORS должен быть ограничен конкретным origin фронтенда (не `*`), настраиваемым через конфигурацию для dev/prod окружений. | `backend/app/main.py::CORSMiddleware(allow_origins=["http://localhost:5173"])` |
| NFR-SEC-06 | Обращения к внешним AI/GitHub/Google API должны быть защищены таймаутами и не должны передавать пользовательские секреты (пароли, JWT) в промпт или во внешний запрос. | архитектура §3 |
| NFR-SEC-07 | Rate limiting AI-эндпоинтов должен использовать паттерн Token/Leaky Bucket в Redis для защиты от исчерпания квоты внешнего провайдера и от злоупотребления одним пользователем. | `bibliography.md` п. 70 |
| NFR-SEC-08 | Валидация входных данных API должна выполняться на границе через Pydantic-схемы (`app/schemas/`), не полагаясь на проверки внутри бизнес-логики. | `backend/app/schemas/diagram.py`, `backend/app/schemas/auth.py` |

## 3. Надёжность и отказоустойчивость

| ID | Требование | Источник |
|---|---|---|
| NFR-REL-01 | Отсутствие AI-ключа не должно приводить к падению системы: при `AI_PROVIDER=stub` (значение по умолчанию) все AI-режимы работают предсказуемо на заглушке. | `backend/app/integrations/ai/stub_provider.py`, `docs/architecture/01-ai-provider-setup.md` |
| NFR-REL-02 | Обращения к внешним сервисам (LLM/VLM API, GitHub API, Google Drive API) должны быть защищены паттернами Circuit Breaker/Bulkhead, чтобы недоступность одного внешнего сервиса не приводила к деградации остальной системы. | `bibliography.md` п. 55 (Release It!) |
| NFR-REL-03 | Ошибки бэкенда должны централизованно логироваться в систему трекинга ошибок (GlitchTip, Sentry-SDK-совместимая), а не теряться в консоли процесса. | архитектура §7, `bibliography.md` п. 54 |
| NFR-REL-04 | Слой `dsl/` и `notations/` должен тестироваться модульно без БД и без сети (чистые unit-тесты) — это уже требование, соблюдаемое в `backend/tests/test_parser.py` и `test_erd_notation.py`, и должно сохраняться для всех новых нотаций последующих волн. | архитектура §4, `backend/tests/` |
| NFR-REL-05 | Уведомления о завершении фоновых задач (рендер, AI-генерация) должны доставляться пользователю через WebSocket по паттерну Publish/Subscribe, с деградацией до опроса (polling), если WebSocket-соединение недоступно. | архитектура §3, п. 3 |

## 4. Наблюдаемость

| ID | Требование | Источник |
|---|---|---|
| NFR-OBS-01 | Система должна вести структурированные логи API и воркер-процесса, пригодные для агрегации (Twelve-Factor App: логи как поток событий). | `bibliography.md` п. 51 |
| NFR-OBS-02 | Ошибки уровня backend/worker должны попадать в GlitchTip с достаточным контекстом (стек вызова, идентификатор запроса) для диагностики без доступа к серверу. | архитектура §7 |
| NFR-OBS-03 | API должен предоставлять автоматически генерируемую OpenAPI-документацию (`/docs`), актуальную относительно Pydantic-схем без ручной синхронизации. | `backend/README.md` (`/docs`), FastAPI |

## 5. Доступность (accessibility)

| ID | Требование | Источник |
|---|---|---|
| NFR-A11Y-01 | Модальные окна (AI-ассистент, документация, история версий) должны иметь корректные ARIA-роли (`role="dialog"`, управление фокусом, закрытие по Esc). | `bibliography.md` п. 38, методичка (лабораторная по семантической разметке) |
| NFR-A11Y-02 | Интерактивные элементы (кнопки, вкладки режимов AI, пункты сайдбара) должны быть доступны с клавиатуры (фокус, `tab-index`, видимое состояние фокуса). | `bibliography.md` п. 38 (WCAG/ARIA) |
| NFR-A11Y-03 | Цветовые пары текст/фон в обеих темах должны обеспечивать достаточный контраст (ориентир — WCAG AA) — обе темы в макетах (`IDE-Dark.dc.html`, `IDE-Light.dc.html`) должны быть проверены отдельно, так как это независимые палитры, а не инверсия одной. | `design/mockups/IDE-Dark.dc.html`, `IDE-Light.dc.html` |

## 6. Совместимость и адаптивность

| ID | Требование | Источник |
|---|---|---|
| NFR-COMPAT-01 | Frontend должен корректно работать в актуальных версиях Chrome/Firefox/Edge (эволюционирующий список — фиксируется отдельно в руководстве пользователя РПЗ, глава 3.1). | методичка, «Требования к окружению» |
| NFR-COMPAT-02 | Раскладка на основе CSS Grid/Flexbox должна поддерживать изменение размеров окна и панелей без поломки вёрстки (см. FR-UI-02). | `bibliography.md` п. 93 |
| NFR-COMPAT-03 | Верстка должна следовать методологии БЭМ для CSS сложного макета редактора, чтобы стили компонентов не конфликтовали при расширении новыми панелями/нотациями. | `bibliography.md` п. 92 |

## 7. Поддерживаемость и расширяемость

| ID | Требование | Источник |
|---|---|---|
| NFR-MAINT-01 | Добавление новой нотации должно требовать только нового модуля в `app/notations/` и его регистрации — без изменения `api/`, `services/`, парсера или frontend-ядра (Open/Closed Principle). | архитектура §5 |
| NFR-MAINT-02 | Слои `api → services → repositories → domain` должны сохранять однонаправленную зависимость внутрь (Dependency Inversion): `services/` не должен зависеть от конкретных реализаций `AIProvider`/`StorageProvider`, только от протоколов в `domain/interfaces.py`. | архитектура §4 |
| NFR-MAINT-03 | Код должен быть без комментариев объясняющего характера внутри тела функций (комментарии допустимы только там, где они формально необходимы — напр. докстринги модуля/протокола для документации архитектуры, как в текущем коде); имена функций/переменных должны делать код самодокументируемым. | явное правило пользователя (см. системный контекст задачи) |
| NFR-MAINT-04 | Статусы задач, коды ошибок, режимы AI, ключи нотаций должны быть определены через `Enum`/строковые константы в одном месте, без «магических строк», разбросанных по коду. | архитектура §4 |
| NFR-MAINT-05 | Каждая волна нотаций должна добавляться без переписывания предыдущих волн — переход между волнами выполняется через рефакторинг-каталог (Фаулер), а не через замену архитектуры. | архитектура §5, `bibliography.md` п. 3 |

## 8. Развёртывание и инфраструктура

| ID | Требование | Источник |
|---|---|---|
| NFR-INFRA-01 | Локальная среда разработки должна подниматься одной командой `docker compose up --build` (api + worker + redis + postgres). | `docker-compose.yml`, `README.md` |
| NFR-INFRA-02 | Backend/DB должны разворачиваться на бесплатных сервисах, одобренных методичкой для доступности из Беларуси (Render/Supabase), frontend — на Netlify/GitHub Pages, CI/CD — GitHub Actions. | архитектура §7, методичка «Приложение Г» |
| NFR-INFRA-03 | Конфигурация окружения должна следовать Twelve-Factor App: все параметры среды — через `.env`/переменные окружения, не через изменение кода при переходе dev→prod. | `bibliography.md` п. 51 |
| NFR-INFRA-04 | CI должен прогонять тесты (`pytest` для backend, `Jest`/RTL для frontend) на каждый push/PR через GitHub Actions. | `bibliography.md` пп. 49, 63–64 |

## 9. PWA и офлайн-режим

| ID | Требование | Источник |
|---|---|---|
| NFR-PWA-01 | Frontend должен автосохранять черновик кода DSL в LocalStorage/IndexedDB до синхронизации с сервером, чтобы не терять правки при обрыве соединения или случайном закрытии вкладки. | `bibliography.md` пп. 73–74 |
| NFR-PWA-02 | Приложение должно поддерживать базовый офлайн-режим через Service Worker и Cache API (доступность интерфейса и последнего загруженного состояния диаграммы без сети). | `bibliography.md` п. 72, методичка (лабораторная по PWA) |
| NFR-PWA-03 | История версий и SVG-превью, не помещающиеся в LocalStorage по объёму, должны кэшироваться через IndexedDB. | `bibliography.md` п. 74 |
