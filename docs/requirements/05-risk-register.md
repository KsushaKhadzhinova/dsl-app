# Реестр рисков проекта

**Статус:** актуально
**Связанные документы:** [`00-overview.md`](00-overview.md), [`04-traceability-matrix.md`](04-traceability-matrix.md), [`../architecture/05-architecture-review.md`](../architecture/05-architecture-review.md)

Риски разделены на **академические** (влияют на защиту курсовой/зачёт по лабораторным) и **технические** (влияют на качество и сопровождаемость продукта). Для каждого — вероятность, влияние и то, что уже сделано или стоит сделать для снижения.

## 1. Академические риски

| ID | Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|---|
| R-01 | Тема не по официальному варианту вызовет вопросы у комиссии | Средняя | Высокое | Уже задокументировано обоснование в `00-system-architecture.md` (методичка допускает FastAPI как альтернативу — модуль 03); держать наготове ссылку на конкретный файл методички при защите |
| R-02 | Курсовой срез (Волна 1) не полностью закрыт: не хватает `uml.class` и `idef0` нотаций, а FR-NOT-06 помечен как обязательный для зачёта | Высокая (уже подтверждено фактом) | Высокое | См. `04-traceability-matrix.md`, итоговое наблюдение — доделать эти два профиля до защиты в приоритете выше новых фич |
| R-03 | Смешение коммитов/веток лабораторных Часть 2 и «допов» для реального продукта запутает проверяющего лабораторные | Средняя | Среднее | Уже введено жёсткое правило: раздельные ветки и коммиты для лаб и допов (см. `docs/labs/00-labs-mapping.md`, обновить после появления новых lab-веток) |
| R-04 | Скриншоты в отчётах по Части 2 лаб 1–2 — не подлинные снимки экрана самой Ксении (частично сгенерированы или взяты из чужого отчёта как референс) | Средняя, если проверяющий сверяет визуально | Среднее | Явно помечено в `REFERENCE_screenshots_from_other_report/README`/`REPORT_screenshots_lab2/README.txt` как чек-лист «сделать самой» — обязательно закрыть до сдачи |
| R-05 | Проверяющий по лабораторным ИТиВП Часть 2 (лабы 3–8, практики 2–4) ожидает буквального соответствия условиям, а требования по ним ещё не сверены с реальным текстом LMS (курс id=7361) | Высокая (сверка ещё не проведена на момент этого документа) | Высокое | Следующий шаг в очереди задач — зайти в LMS и прочитать реальный текст каждой лабы перед реализацией, как уже было сделано для Части 1 |

## 2. Технические риски

| ID | Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|---|
| R-06 | Совместное редактирование (FR-AUTH-08) без стратегии разрешения конфликтов одновременных правок может испортить состояние диаграммы при гонке двух клиентов | Высокая, если реализовать «как есть» (broadcast без merge) | Высокое | См. архитектурный аудит: рекомендация — простой locking («один активный редактор» / turn-based) вместо полноценного OT/CRDT на этом масштабе проекта |
| R-07 | Фоновый агент реализовал BPMN-нотацию (Волна 4) раньше запланированной волны — расхождение между документированным планом волн и фактическим кодом | Уже произошло | Низкое-среднее | Не откатывать — обновить `00-system-architecture.md` §5, отметить `bpmn` как «реализовано раньше графика», пересчитать актуальный состав Волны 1 факта vs плана |
| R-08 | Нет сущности «пространство/проект» (workspace) для многофайловых диаграмм (FR-DSL-11/12), а UI уже подразумевает файловый список в сайдбаре | Средняя (проявится при Волне 3) | Среднее | Заложить модель заранее (см. архитектурный аудит, п. 3), а не мигрировать по факту наступления Волны 3 |
| R-09 | Redis используется одновременно как очередь задач, кэш рендера и rate-limiter без явного разделения пространств ключей/БД-индексов | Низкая при текущем масштабе | Низкое | Зафиксировать префиксы ключей (`queue:*`, `cache:render:*`, `ratelimit:ai:*`) сейчас, пока данных мало и миграция дешёвая |
| R-10 | Нет решения по refresh-токенам — JWT только с access-токеном, без описанной политики истечения/обновления | Средняя | Среднее | Определить срок жизни access-токена и стратегию (короткий токен + повторный логин, либо refresh-токен) до реализации реального продакшн-доступа |
| R-11 | Реальный Neon PostgreSQL и его переменные окружения ещё не переданы боту — backend/frontend написаны «как есть» без возможности сквозного теста на реальной БД | Высокая (текущее состояние) | Среднее | Уже принято решение: строить корректно против существующей конфигурации, дать Ксении точную инструкцию по подключению `DATABASE_URL`, когда основной функционал устоится |
| R-12 | Требование адаптивности (FR-UI-12) для логина/регистрации не было явно проверено в браузере на момент написания этого документа | Средняя | Низкое | Проверить в Claude Browser (`resize_window` mobile/tablet presets) после того как фронтенд-агент завершит работу |

## 3. Как использовать этот реестр

Перед защитой курсовой или сдачей очередной лабораторной — пройтись по разделу 1 (академические риски) как по чек-листу. Перед тем как начинать новую волну нотаций/фич — пройтись по разделу 2 и закрыть то, что помечено «Высокая вероятность» и «Высокое влияние» в первую очередь.
