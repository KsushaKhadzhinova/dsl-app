## 2. Нотации и валидация

| ID | Волна | Требование | Источник |
|---|---|---|---|
| FR-NOT-01 | 1 | Система должна реализовывать реестр нотаций как открытый для расширения набор плагинов (`NotationProfile`), где добавление новой нотации не требует изменения ядра парсера, API или фронтенда. | `backend/app/notations/__init__.py`, архитектура §5 |
| FR-NOT-02 | 1 | Система должна поддерживать нотацию **ERD, стиль Crow's Foot, логический уровень** (`erd.crows_foot.logical`): узлы вида `entity` с атрибутом `pk`, связи между сущностями. | `backend/app/notations/erd.py` |
| FR-NOT-03 | 1 | Система должна проверять структурную валидность диаграммы: недопустимый тип узла для выбранной нотации — ошибка; связь, ссылающаяся на несуществующий узел, — ошибка; отсутствие первичного ключа у сущности ERD — предупреждение (не блокирует рендер). | `backend/app/notations/erd.py::validate`, `backend/tests/test_erd_notation.py` |
| FR-NOT-04 | 1 | Система не должна выполнять рендер, если среди результатов валидации есть хотя бы одна ошибка уровня `error`; при этом предупреждения (`warning`) рендер не блокируют. | `backend/app/services/diagram_service.py::render` |
| FR-NOT-05 | 2 | Система должна поддержкивать UML: **use case, sequence, activity, state machine**; IDEF3 (PFDD); DFD (с декомпозицией по уровням, аналогично IDEF0). | архитектура §5, «Волна 2» |
| FR-NOT-06 | 1 | Система должна поддерживать UML **class diagram** и **IDEF0 (контекст + декомпозиция)** в объёме, достаточном для курсового среза. | архитектура §5, «Волна 1» |
| FR-NOT-07 | 3 | Система должна поддерживать оставшиеся диаграммы UML (object, component, composite structure, deployment, package, profile, communication, interaction overview, timing) — все 13 канонических видов суммарно. | архитектура §5, «Волна 3» |
| FR-NOT-08 | 3 | Система должна поддерживать **IDEF1X** как отдельную от ERD нотацию (со своим разделением уровней), **IDEF3 OSTN**, а также остальные комбинации ERD: уровни concept/logical/physical × нотации Crow's Foot/Chen/UML-class. | архитектура §5, «Волна 3» |
| FR-NOT-09 | 4 | Система должна поддерживать **BPMN** всех 4 видов (process, collaboration, choreography, conversation) и **сети Петри** всех структур (state machines, marked graphs, ordinary, generalized) и типов (colored, timed, stochastic, inhibitor), включая ООП-сети как отдельный профиль. | архитектура §5, «Волна 4» |
| FR-NOT-10 | 4 | Для сетей Петри система должна строить граф достижимости и проверять свойства (достижимость, живость, ограниченность) для **ограниченных (bounded)** сетей разумного размера; для неограниченных/слишком больших сетей — явно сообщать о невозможности полного анализа, а не давать неверный результат. | архитектура §5, честная оговорка про EXPSPACE-полноту |
| FR-NOT-11 | 3 | Для IDEF0 система должна проверять ICOM-полноту (каждый блок декомпозиции имеет как минимум одну входную/управляющую/исходящую/механизм-связь, согласованную с родительской диаграммой). | архитектура §5 |
| FR-NOT-12 | 3 | Для IDEF1X система должна проверять корректность миграции внешних ключей между родительскими и дочерними сущностями. | архитектура §5 |
| FR-NOT-13 | 1 | Пользователь может увидеть список ошибок/предупреждений валидации во вкладке **Problems** нижней панели, с указанием строки/столбца и текста сообщения. | `design/mockups/Validation.dc.html` |
| FR-NOT-14 | 1 | Система должна подсвечивать в редакторе строку с предупреждением волнистым подчёркиванием и жёлтым фоном, не блокируя ввод. | `design/mockups/Validation.dc.html` (`.warn-line`) |
