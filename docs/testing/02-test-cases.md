# Тест-кейсы — функциональность и бизнес-логика

**Статус:** актуально
**Связанные документы:** [`01-requirements-testability-review.md`](01-requirements-testability-review.md), [`../requirements/03-use-cases.md`](../requirements/03-use-cases.md)

Формат: ID, Название, Техника проектирования (см. `test-design-techniques.md` из скилла `qa-tester`), Приоритет, Предусловия, Шаги, Ожидаемый результат. Позитивные и негативные сценарии даны вместе для каждой функции, а не отдельным списком — так виднее, какого негативного случая не хватает.

## 1. Регистрация и вход (FR-AUTH-01…03, 05)

**Техника: Equivalence Partitioning (класс email/пароля) + BVA (длина полей) + Error Guessing**

| ID | Название | Приоритет | Шаги | Ожидаемый результат |
|---|---|---|---|---|
| TC-AUTH-01 | Успешная регистрация с валидными данными | High | 1. Открыть `/register`. 2. Ввести уникальный email, username, пароль (≥8 символов), подтверждение пароля совпадает. 3. Отправить форму. | `POST /api/v1/auth/register` → 201/200; пользователь создан; пароль не возвращён в ответе (NFR-SEC-01); редирект на `/` или на `/login` в зависимости от контракта. |
| TC-AUTH-02 | Регистрация с уже занятым email | High | Повторить TC-AUTH-01 с тем же email второй раз. | 400 с понятным сообщением («email уже занят»); в БД не создаётся вторая запись User с тем же email. |
| TC-AUTH-03 | Регистрация с пустым полем email | Medium | Оставить email пустым, остальные поля валидны. Отправить. | Форма не отправляется / backend возвращает 422 (Pydantic validation) — до создания записи в БД. |
| TC-AUTH-04 | Регистрация с невалидным форматом email («not-an-email») | Medium | Ввести строку без `@` в поле email. | 422 до создания записи; сообщение об ошибке формата. |
| TC-AUTH-05 | Регистрация с несовпадающими паролем и подтверждением | Medium | Пароль и «повтор пароля» отличаются. | Клиентская валидация блокирует отправку; ошибка показана без потери введённых значений. |
| TC-AUTH-06 | Успешный вход с верными данными | High | Войти с email/паролем, созданными в TC-AUTH-01. | 200 + JWT access_token в ответе; токен сохранён в localStorage; редирект на `/`. |
| TC-AUTH-07 | Вход с неверным паролем | High | Верный email, неверный пароль. | 401, без указания что именно неверно — email или пароль (не раскрывать, какой из двух факторов ошибочен — общая практика защиты от enumeration). |
| TC-AUTH-08 | Вход с несуществующим email | High | Email, которого нет в системе. | 401 с тем же сообщением, что и TC-AUTH-07 (симметрично, не должно быть различимо для атакующего). |
| TC-AUTH-09 | Доступ к `/` без токена | High | Открыть `/` в приватном окне без предварительного логина. | Редирект на `/login`, IDE не отрисовывается вообще (не «мелькает» перед редиректом). |
| TC-AUTH-10 | Доступ к `/` с истёкшим/невалидным токеном | High | Подменить localStorage-токен на заведомо невалидную строку, открыть `/`. | Любой запрос к API возвращает 401 → клиент разлогинивает и редиректит на `/login` (см. диаграмму состояний `../architecture/04-state-diagrams.md`, п.4). |

## 2. Написание/рендер DSL и валидация нотаций (FR-DSL-02…06, FR-NOT-02…04)

**Техника: Decision Table (комбинация «есть синтаксическая ошибка» × «есть ошибка валидации» × «есть только предупреждение») + Use Case Testing**

| Rule | Синтаксис валиден? | Валидация: error? | Валидация: warning? | Ожидаемый результат |
|---|---|---|---|---|
| 1 | Нет | — | — | Рендер не выполняется; возвращается позиция ошибки (строка/столбец); канвас не обновляется |
| 2 | Да | Да | — | Рендер не выполняется (FR-NOT-04); Problems показывает ошибку(и) |
| 3 | Да | Нет | Да | Рендер выполняется; Problems показывает предупреждение (напр. ERD-сущность без PK) |
| 4 | Да | Нет | Нет | Рендер выполняется; Problems пуст |

| ID | Название | Приоритет | Шаги | Ожидаемый результат |
|---|---|---|---|---|
| TC-DSL-01 | Rule 1 — синтаксическая ошибка | High | Ввести DSL с незакрытой скобкой/пропущенной кавычкой. Нажать Run. | 400 с `DslSyntaxError`, точная строка/столбец; строка подсвечена в редакторе (FR-NOT-14 для warning-подобной подсветки, но здесь — синтаксис, должно быть однозначно видно, что это блокирующая ошибка, не предупреждение). |
| TC-DSL-02 | Rule 2 — валидная связь на несуществующий узел (ERD) | High | `entity A`, связь `A -> B`, где `B` не объявлен. Run. | Ошибка валидации «связь ссылается на несуществующий узел»; рендер не происходит; канвас не обновляется (остаётся прошлый успешный рендер или пуст, если рендера ещё не было — уточнить конкретное поведение при первом прогоне). |
| TC-DSL-03 | Rule 3 — ERD-сущность без PK | Medium | `entity Order { name text }` без атрибута `pk`. Run. | Рендер выполняется успешно; Problems показывает 1 warning «отсутствует первичный ключ»; канвас показывает сущность. |
| TC-DSL-04 | Rule 4 — валидная минимальная ERD-диаграмма | High | Две сущности с PK и связью между ними. Run. | Рендер успешен; Problems пуст; SVG содержит оба узла и связь. |
| TC-DSL-05 | Комментарии игнорируются парсером | Low | Добавить `// комментарий` внутри валидного DSL. Run. | Комментарий не влияет на результат парсинга/рендера. |
| TC-DSL-06 | BPMN: узел без стартового события | Medium | Диаграмма BPMN только с задачами, без `start`/`end` событий. Run. | Ошибка валидации «отсутствует обязательное стартовое/конечное событие» (согласно отчёту бэкенд-агента о профиле bpmn.process). |
| TC-DSL-07 | BPMN: sequence flow на несуществующий узел | Medium | Связь ссылается на несуществующий task/event ID. | Ошибка валидации, аналогично TC-DSL-02, но в контексте BPMN. |
| TC-DSL-08 | Переключение нотации после ввода кода | Medium | Ввести валидный ERD-код, затем переключить нотацию на BPMN без изменения кода. Run. | Ошибка валидации «недопустимый тип узла для выбранной нотации» (не тихий пропуск и не краш). |

## 3. Версионирование (FR-VER-01…04, 07)

**Техника: State Transition Testing + Error Guessing (двойной сабмит)**

| ID | Название | Приоритет | Шаги | Ожидаемый результат |
|---|---|---|---|---|
| TC-VER-01 | Первое сохранение создаёт diagram + commit + blob | High | Написать DSL, нажать Save с новым названием диаграммы. | Создана запись `Diagram`, `Commit`, `Blob`; `Blob.content_hash` = sha256(DSL-текста). |
| TC-VER-02 | Повторное сохранение идентичного кода не создаёт новый Blob | High | Сохранить диаграмму дважды подряд без изменения кода. | Второй `Commit` ссылается на тот же `Blob.id`, что и первый (дедупликация по FR-VER-02); в БД не появляется второй Blob с тем же hash. |
| TC-VER-03 | Изменённый код создаёт новый Blob | Medium | Изменить DSL-текст, сохранить снова. | Новый `Blob` с новым hash; новый `Commit` на диаграмму. |
| TC-VER-04 | Двойной клик Save (гонка/дублирующий запрос) | Medium | Быстро дважды нажать Save на одном и том же неизменном коде (или отправить два одинаковых `POST .../versions` подряд, как в API-тестах). | Не должно создаваться два разных commit с одинаковым содержимым как отдельные «настоящие» версии, если это один пользовательский клик — либо второй запрос игнорируется/дедуплицируется, либо (если оба обрабатываются как два разных сохранения) — это осознанное поведение, которое нужно явно подтвердить с разработчиком, а не считать умолчательно правильным (см. `qa-tester`: не изобретать ожидаемое поведение для неоднозначного случая). |
| TC-VER-05 | Автор версии — `user`, а не `ai` при ручном сохранении | Medium | Сохранить диаграмму без использования AI. | `Commit.author == "user"`. |

## 4. AI-квота (FR-AI-12) — BVA на точной границе 20/день

**Техника: Boundary Value Analysis**

| ID | Название | Приоритет | Шаги | Ожидаемый результат |
|---|---|---|---|---|
| TC-AIQ-01 | 19-й запрос за день | High | Сделать 19 AI-запросов подряд одним пользователем в течение одного дня (используя `StubAIProvider`, чтобы не тратить реальную квоту провайдера). | Все 19 успешны (200), счётчик Redis = 19. |
| TC-AIQ-02 | Ровно 20-й запрос | High | Сделать 20-й запрос тем же пользователем в тот же день. | Успешен (200) — согласно трактовке «20 включительно» из `01-requirements-testability-review.md`, раздел 2. |
| TC-AIQ-03 | 21-й запрос — превышение квоты | High | Сделать 21-й запрос тем же пользователем в тот же день. | 429 с сообщением о превышении дневного лимита; запрос НЕ уходит к AI-провайдеру (важно проверить это, а не только код ответа — см. `api-testing.md`: совпадение статус-кода не доказательство правильного поведения). |
| TC-AIQ-04 | Сброс квоты на следующий день | Medium | После TC-AIQ-03 дождаться (или симулировать через TTL/мок времени) наступления следующего дня. Сделать запрос. | Запрос успешен; счётчик сброшен на 0→1. |
| TC-AIQ-05 | Квота считается по пользователю, не глобально | Medium | Пользователь A делает 20 запросов (исчерпывает квоту); пользователь B делает 1 запрос в тот же день. | Запрос пользователя B успешен — квоты изолированы по `user_id`. |

## 5. Совместное редактирование и доступ (FR-AUTH-06, FR-AUTH-08) — Decision Table

**Техника: Decision Table + Error Guessing.** Важная оговорка (см. риск R-06 в реестре рисков): без реализованной стратегии разрешения конфликтов эти тест-кейсы покрывают только happy-path доступа, не одновременное редактирование одного диапазона текста — это осознанно вне текущего охвата, не «забыто».

| Rule | Роль запрашивающего | Владелец? | Соавтор? | Ожидаемый доступ |
|---|---|---|---|---|
| 1 | — | Да | — | Полный доступ (чтение/запись/управление соавторами) |
| 2 | — | Нет | Да (editor) | Чтение и запись, без управления соавторами |
| 3 | — | Нет | Нет | 404 (не 403 — FR-AUTH-06: не раскрывать факт существования чужой диаграммы) |

| ID | Название | Приоритет | Шаги | Ожидаемый результат |
|---|---|---|---|---|
| TC-ACC-01 | Владелец видит и редактирует свою диаграмму | High | Войти как владелец, открыть диаграмму. | 200, полный доступ. |
| TC-ACC-02 | Посторонний пользователь получает 404, а не 403 | High | Войти как пользователь Б без прав на диаграмму пользователя А, запросить `GET /diagrams/{A's id}` напрямую по API. | 404, не 403 — тело ответа не должно содержать никаких метаданных диаграммы (даже частичных). |
| TC-ACC-03 | Соавтор (editor) может редактировать, но не добавлять других соавторов | Medium | Владелец добавляет Б соавтором. Б редактирует и сохраняет версию — должно получиться. Б пытается добавить В соавтором — должно быть отклонено. | Редактирование 200; добавление соавтора третьим лицом — 403 (здесь уже допустимо различать 403 от 404, так как Б **знает** о существовании диаграммы легитимно). |
| TC-ACC-04 | Удалённый соавтор теряет доступ | Medium | Владелец удаляет Б из соавторов. Б повторяет `GET` того же id. | 404 (не 403) — после удаления Б для системы неотличим от постороннего. |
