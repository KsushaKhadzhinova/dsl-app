# Test Plan — DiagramCode

**Статус:** актуально
**Связанные документы:** [`../requirements/01-functional-requirements.md`](../requirements/01-functional-requirements.md), [`../requirements/02-nonfunctional-requirements.md`](../requirements/02-nonfunctional-requirements.md), [`01-requirements-testability-review.md`](01-requirements-testability-review.md)

## 1. Объект тестирования

DiagramCode — сервис для описания диаграмм через собственный DSL: backend (FastAPI), frontend (React + Monaco IDE). Тестируется функционал Волны 1 (курсовой срез) и уже реализованные точечные фрагменты Волны 2 (совместное редактирование, декомпозиция, BPMN) — см. `../requirements/04-traceability-matrix.md` за точным статусом на момент написания.

## 2. Цели тестирования

Дать команде (то есть самой себе как разработчику и будущему проверяющему на защите) уверенность, что:
- Основной пользовательский путь (регистрация → вход → написание DSL → рендер → сохранение) работает без потери данных и без ложных ошибок.
- Валидация нотаций корректно отличает ошибку от предупреждения (FR-NOT-04) и не пропускает недопустимые диаграммы.
- Границы (AI-квота, размер загружаемого изображения, длина полей) обрабатываются точно по заявленному значению, а не «примерно».
- Авторизация не даёт доступа к чужим диаграммам ни на уровне UI, ни через прямой вызов API.

Не цель — исчерпывающее тестирование каждой комбинации (невозможно и не нужно); приоритет — риск-ориентированный, по компонентам, чьи дефекты дороже всего пропустить (auth, платёжного эквивалента здесь нет, но AI-квота и версии — ближайший аналог «дорогих» операций).

## 3. Область (Scope)

**In scope:**
- Backend API: auth, diagrams CRUD/версии/рендер/экспорт, AI-эндпоинт с квотой, нотации ERD и BPMN, декомпозиция, соавторство.
- Frontend: логин/регистрация, IDE-оболочка (Monaco, канвас, статус-бар, тема, язык), поток Run/Save/Export/Import.
- Интеграция frontend↔backend по реальным контрактам (см. `04-traceability-matrix.md` в этой же папке за списком проверенных эндпоинтов).

**Out of scope (пока не реализовано или сознательно исключено — см. FR-волны):**
GitHub/Google Drive OAuth, AI-модалка (UI), история версий/diff (UI), realtime collaborative UI, IDEF0/UML class/Petri/DFD нотации (не зарегистрированы в `notations/`).

## 4. Подход

- **Функциональное тестирование** — black-box, по требованиям FR-*, техники подобраны по форме требования (см. `02-test-cases.md`).
- **API-тестирование** — напрямую против FastAPI-эндпоинтов (см. `03-api-test-cases.md`), независимо от готовности UI — оправдано тем, что backend и frontend в этом проекте разрабатывались/менялись параллельно двумя независимыми агентами.
- **Регрессионное тестирование** — не отдельная фаза здесь: автоматические наборы (`backend/tests/`, `frontend/tests/`) уже выполняют эту роль на каждый прогон; ручные тест-кейсы в этом документе — то, что автотесты пока не покрывают (граничные сценарии авторизации между пользователями, UI-состояния канваса).
- **Тестирование NFR** — ограничено тем, что реально проверяемо без прод-окружения (см. `01-requirements-testability-review.md` — часть NFR помечена как непроверяемая до появления конкретных числовых порогов).

## 5. Тестовое окружение

| Окружение | Назначение | Данные |
|---|---|---|
| Локальное (Docker Compose: api + worker + redis + postgres) | Основная среда ручного/API-тестирования | Тестовые пользователи, созданные вручную; не прод-данные |
| CI (GitHub Actions) | Автотесты (`pytest`, `Jest`) на каждый push/PR | Изолированная тестовая БД/fakeredis, без сети |

На момент написания реальная Neon PostgreSQL ещё не подключена к среде разработки бота — часть тестов из `03-api-test-cases.md`, требующих реальной БД, проверены агентами через `pytest`/`fakeredis`-моки; сквозная проверка на реальной БД — открытый пункт (см. риск R-11 в `../requirements/05-risk-register.md`).

## 6. Роли и ответственность

Один человек (Ксения) совмещает роли PO/разработчика/тестировщика в рамках курсовой работы; фоновые агенты выполняют реализацию и пишут собственные автотесты для своего кода — эти автотесты не заменяют независимую сверку тест-кейсов с реальными требованиями (см. риск качества автотестов в `test-documentation.md`: «покрытие тестом не значит, что тест хорошо написан»).

## 7. Критерии входа (Entry criteria)

- Требование (FR/NFR ID) существует и прошло проверку тестируемости (`01-requirements-testability-review.md`) — не тестируем то, для чего не определён ожидаемый результат.
- Соответствующий код смёржен в тестируемую ветку и автотесты для него зелёные.

## 8. Критерии выхода (Exit criteria)

Тестирование конкретной фичи считается завершённым, когда:
- Все тест-кейсы приоритета High/Medium из `02-test-cases.md`/`03-api-test-cases.md` выполнены.
- Нет открытых дефектов severity Blocker/Critical по этой фиче.
- Открытые дефекты Major и ниже задокументированы и осознанно приняты (не «забыты») — см. `05-defect-report-template.md`.

Exit criteria не означает «ноль багов» — означает, что оставшийся риск известен и принят осознанно.

## 9. Риски и допущения

См. `../requirements/05-risk-register.md` — раздел 2 (технические риски) прямо пересекается с тестовым риском: например риск R-06 (конфликты совместного редактирования) означает, что тестировать совместное редактирование сейчас можно только на happy path (см. пометку в `02-test-cases.md`, TC-COLLAB-*).

## 10. Артефакты (Deliverables)

- `01-requirements-testability-review.md` — обзор тестируемости FR/NFR.
- `02-test-cases.md` — тест-кейсы по функциональным требованиям (UI + бизнес-логика), с указанной техникой проектирования.
- `03-api-test-cases.md` — тест-кейсы по API-эндпоинтам.
- `04-traceability-matrix.md` — трассируемость Требование → Тест-кейс.
- `05-defect-report-template.md` — шаблон баг-репорта и шкалы severity/priority, адаптированные под проект.
