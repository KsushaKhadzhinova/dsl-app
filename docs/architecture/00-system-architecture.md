# Архитектура системы DiagramCode — исследование и решение

**Статус:** принято к реализации
**Контекст:** курсовая работа по дисциплине «Интернет-технологии и веб-программирование» (ИТиВП, БГУИР), выполняемая не по типовому варианту тем (см. `E:\ИТиВП\Часть 2\Курсовое проектирование\01. Темы КП.pdf`) — тема согласована отдельно.

## 1. Два слоя требований — и почему это не противоречие

Официальный шаблон РПЗ (`Часть 2/Курсовое проектирование/03...pdf`) описывает **скромный по объёму** проект: React + Node.js/Express + PostgreSQL/MongoDB, JWT-аутентификация, ≥3 функциональных модуля, объём работы — 30 часов, 25–30 страниц РПЗ. Это минимальная планка для зачёта.

Отдельно от этого — твоё требование: enterprise-grade, распределённая архитектура, максимальная глубина нотаций и валидации. Это не конфликт, а **два среза одной системы**:

- **Целевая архитектура** (этот документ) — то, как система спроектирована и куда она растёт: чистые границы модулей, расширяемый реестр нотаций, асинхронная обработка тяжёлых задач, наблюдаемость.
- **Курсовой срез** — честное подмножество той же системы (не отдельная демо-заглушка), которого достаточно, чтобы закрыть 3 обязательных модуля из РПЗ и уложиться в 30 часов: DSL-редактор + рендер + сохранение + одна нотация с валидацией + auth. Остальное достраивается поверх той же архитектуры после сдачи, без переписывания.

Это соответствует и «Чистому коду» (не проектировать сверх того, что нужно *сейчас*, но и не закрывать себе пути), и здравому смыслу distributed systems литературы: расширяемость закладывается через границы и контракты, а не через то, что всё сразу реализовано.

## 2. Почему бэкенд — Python/FastAPI, а не Node.js/Express (как в шаблоне РПЗ)

Шаблон РПЗ называет Node.js/Express дефолтом, но в самой программе курса это **не единственный одобренный путь**: `Часть 2/Модуль 03. Альтернативные технологии/01. Сравнение Node.js и Python/FastAPI.pdf` прямо разбирает переход на FastAPI как законную альтернативу, с отдельными презентациями про создание API на FastAPI, автогенерацию OpenAPI-документации и валидацию данных. То есть отклонение от Node.js — не самодеятельность, а путь, явно предусмотренный программой; в разделе 2.1 РПЗ («Выбор и обоснование технологического стека») это нужно будет аргументировать именно так — со ссылкой на модуль 03.

Почему FastAPI важен именно для этого проекта (не абстрактно, а по сути задачи):

| Критерий | Node.js/Express (дефолт РПЗ) | Python/FastAPI (выбор проекта) |
|---|---|---|
| Парсинг собственного DSL | Слабая экосистема парсер-генераторов | `Lark`/`textX` — грамматики на чистом Python, быстрая итерация над языком |
| AI-интеграция (LLM/VLM) | SDK есть, но менее зрелые примитивы для промпт-инжиниринга | Python — де-факто стандарт для работы с LLM/VLM, лучшая экосистема |
| Асинхронная обработка (рендер, AI) | Возможно (worker\_threads, BullMQ) | Тот же уровень зрелости (Celery/RQ/Arq + Redis), плюс общий язык с парсером |
| Типизация и автодокументация API | Нужен доп. слой (Zod, OpenAPI-плагины) | Pydantic-схемы → OpenAPI из коробки — совпадает с целью модуля 03 |

Это решение — компромисс: FastAPI не «быстрее» Express в вебсерверных бенчмарках принципиально, но для *этого конкретного* проекта (парсер + AI + типизированный контракт) он снимает больше архитектурного трения. Компромисс, а не догма — если на защите потребуют обосновать, аргумент такой.

## 3. Архитектурный стиль: модульный монолит с чёткими границами, а не микросервисы «по умолчанию»

Важное осознанное решение, и оно **не** «максимум сервисов ради распределённости». И Сэм Ньюман («Building Microservices»), и Мартин Фаулер («MonolithFirst») прямо предостерегают: распределять систему там, где нет реальной причины (независимое масштабирование, независимый деплой, изоляция отказа), — это добавленная сложность (сеть, консистентность, наблюдаемость) без выгоды. Настоящее применение «заветов» этих книг — не «побольше сервисов», а **распределять именно то, что реально того требует**, и оставить единым то, что не требует.

Где в этой системе распределение — реальная, а не декоративная необходимость:

1. **Рендеринг и парсинг DSL** — CPU-bound, может быть медленным на больших диаграммах, не должен блокировать HTTP-запрос → **очередь задач** (Redis + RQ/Arq), отдельный пул воркеров, масштабируемый независимо от API.
2. **Обращения к AI (LLM/VLM)** — I/O-bound, сетевые задержки внешнего провайдера, нужны retry/circuit breaker/rate-limit → тоже воркер-пул, с собственными таймаутами, не delящий ресурсы с API-процессом.
3. **Уведомления о готовности задачи** (рендер завершён, AI сгенерировал код) — классический **Publish/Subscribe** паттерн (Burns, «Designing Distributed Systems») — через WebSocket, что прямо совпадает с лабораторной `Часть 2/Модуль 03/12. Лабораторная работа №7 Реализация реального времени с WebSocket`.

Всё остальное (CRUD диаграмм, аутентификация, версии, шаблоны) — **один деплоймый API-процесс** с чистой слоистой архитектурой внутри (`routers → services → repositories → models`), потому что здесь нет independent-scaling причины городить отдельные сервисы — это и есть Clean Architecture/Clean Code уровень, а не distributed systems уровень.

Итоговая топология (логическая, не обязательно физические машины):

```
┌─────────────┐      ┌──────────────────────────────┐      ┌─────────────┐
│   React PWA │─────▶│      API Gateway (Nginx)      │◀────▶│  WebSocket  │
│  (frontend) │      └──────────────┬────────────────┘      │  (уведомления)│
└─────────────┘                     │                        └─────────────┘
                                     ▼
                      ┌──────────────────────────┐
                      │   FastAPI Core Service    │
                      │  routers/services/repos   │
                      │  (auth, diagrams, версии, │
                      │   шаблоны, экспорт-мета)  │
                      └──────────┬────────────────┘
                                 │ ставит задачи
                                 ▼
                      ┌──────────────────────┐        ┌───────────────┐
                      │  Redis (очередь +     │◀──────▶│  PostgreSQL   │
                      │  кэш + rate limit)    │        │  (основное    │
                      └──────────┬────────────┘        │   хранилище)  │
                                 ▼
                 ┌───────────────────────────────┐
                 │   Worker pool (RQ/Arq)         │
                 │  — DSL parse/validate/render   │
                 │  — AI text→DSL, image→DSL      │
                 │  — экспорт в DOT/Mermaid/...    │
                 └──────────┬────────────────────┘
                            ▼
              внешние сервисы: LLM/VLM API, Kroki/Graphviz,
              GitHub API, Google Drive API
```

Это уже настоящая распределённая система (несколько независимо масштабируемых процессов, асинхронная коммуникация через очередь, pub/sub для realtime), но без искусственного дробления там, где в этом нет смысла.

## 4. Слоистая структура ядра (Clean Architecture / Clean Code)

Внутри `FastAPI Core Service` и внутри worker-пула — одинаковый принцип слоёв (согласно Роберту Мартину: зависимости смотрят внутрь, к доменной логике, а не наружу, к фреймворку):

```
app/
├── api/            # routers — только HTTP-контракт (валидация входа через Pydantic, вызов service, сериализация ответа)
├── services/        # бизнес-логика — ничего не знает про FastAPI/HTTP
├── repositories/     # доступ к данным — единственное место с SQL/ORM-запросами
├── domain/          # доменные модели и интерфейсы (Protocol/ABC) — ядро, не зависящее ни от чего
├── schemas/         # Pydantic DTO — вход/выход API, отделены от доменных моделей
├── dsl/             # лексер/парсер/AST/валидаторы — чистый Python, тестируется без БД и без сети
├── notations/       # плагины нотаций (см. §5) — реализуют интерфейсы из domain/
├── integrations/    # адаптеры к внешнему миру: LLM-провайдеры, GitHub, Google Drive, Kroki
└── core/            # конфигурация, DI-контейнер, логирование, безопасность
```

Ключевые принципы Clean Code, применённые буквально (не декларативно):
- **Dependency Inversion**: `services/` зависят от интерфейсов в `domain/` (`StorageProvider`, `RenderEngine`, `AIProvider`), а не от конкретных `GitHubProvider`/`KrokiRenderEngine` — конкретную реализацию подставляет DI-контейнер в `core/`. Это то же самое, что ты видела в исследовании Gemini про `CloudStorage` interface + `GitHubProvider` — только доведено до реального кода, а не только диаграммы классов.
- **Single Responsibility**: один файл — один класс — одна причина для изменения (`DSLLexer` не знает о рендеринге, `BpmnValidator` не знает о Petri-сетях).
- **Маленькие функции, говорящие имена**: без всеобъемлющих `process_everything()`.
- **Никаких магических чисел/строк** — нотации, статусы задач, коды ошибок — через `Enum`.
- Тесты как документация (pytest) — для `dsl/` и `services/` не нужны ни БД, ни сеть — только чистые unit-тесты, что естественно из-за слоистости.

## 5. Реестр нотаций как plugin-архитектура (Open/Closed Principle)

Раз нужны **все** типы UML, ERD (все уровни × все стили), оба варианта IDEF3, IDEF1X отдельно от ERD, все структуры/типы сетей Петри и все виды BPMN — единственный разумный способ не утонуть в частных `if notation == "uml_sequence"` по всему коду — реестр плагинов:

```python
# domain/notation.py
class NotationProfile(Protocol):
    key: str                        # "uml.sequence", "erd.crows_foot.logical", "petri.colored.ordinary"
    display_name: str
    allowed_node_kinds: set[NodeKind]
    allowed_edge_kinds: set[EdgeKind]
    def validate(self, model: DiagramModel) -> list[ValidationIssue]: ...
    def layout_hints(self, model: DiagramModel) -> LayoutHints: ...
    def render(self, model: DiagramModel) -> RenderTree: ...
```

Каждая нотация — отдельный модуль в `notations/`, регистрирующий себя в общем реестре при старте приложения. Добавление новой нотации = новый файл + регистрация, **без изменения** ядра парсера, API или фронтенда (только в дропдауне появляется новый пункт из реестра). Это прямая реализация Open/Closed Principle и то, что реально снимает риск «все типы диаграмм» — это делает архитектуру бесконечно расширяемой *с первого дня*, при этом сами плагины дописываются волнами:

**Волна 1 (курсовой срез, все 3 обязательных модуля РПЗ закрываются здесь):**
`erd.crows_foot.logical`, `uml.class`, `idef0.context+decomposition`

**Волна 2:** `uml.use_case`, `uml.sequence`, `uml.activity`, `uml.state_machine`, `idef3.pfdd`, `dfd`

**Волна 3:** остальные UML (object, component, composite structure, deployment, package, profile, communication, interaction overview, timing), `idef1x` отдельно от `erd`, `idef3.ostn`, ERD-варианты Chen/UML-class, ERD физический/концептуальный уровни

**Волна 4 (после MVP):** BPMN (process → collaboration/choreography/conversation), Petri Nets (ordinary → state machines/marked graphs/generalized, затем colored/timed/stochastic/inhibitor, ООП-сети как отдельный профиль)

Про **глубину валидации** (ты просила «по максимуму») — честно: для структурных проверок (обязательные start/end, отсутствие висячих связей, допустимые пары узел/связь, ICOM-полнота IDEF0, корректность миграции ключей IDEF1X) — да, реализуемо полностью и будет сделано по максимуму. Для формального анализа сетей Петри (достижимость, живость) — это в общем случае вычислительно тяжёлая задача (EXPSPACE-полнота проблемы достижимости), поэтому «максимум» здесь означает: реализовать анализ через построение графа достижимости для *ограниченных* (bounded) сетей разумного размера — это покрывает подавляющее большинство учебных и практических диаграмм, но не является универсальным решателем для любой сети. Это не ограничение архитектуры, а фундаментальное ограничение предметной области, о котором стоит явно написать в РПЗ — как раз демонстрирует понимание глубины темы.

## 6. Хранение и версионирование (git-подобная модель)

PostgreSQL — не MongoDB: версионирование (коммиты, блобы, откаты, диффы) — это по сути граф со строгими связями и ссылочной целостностью, для чего реляционная модель подходит прямо лучше (это уже была верная интуиция в исследовании через Gemini — таблицы `users / diagrams / commits / blobs`, blob разделён от commit для дедупликации одинакового кода между версиями). Redis — не как база данных, а как: очередь задач (RQ/Arq), кэш рендер-результатов (одинаковый DSL + нотация → не пересчитывать SVG), и как movable-window rate-limiter для AI-эндпоинтов (защита от исчерпания бесплатной квоты AI-провайдера).

## 7. Инфраструктура и деплой — привязано к тому, что реально доступно

`Приложение Г` методички прямо называет Heroku/Vercel/AWS потенциально недоступными для Беларуси и даёт конкретный одобренный список — используем его буквально, это не только этично совпадает с методичкой, но и реально бесплатно:

| Слой | Выбор | Почему |
|---|---|---|
| Frontend (статика) | **Netlify** или GitHub Pages | Бесплатный SSL, кастомный домен, авто-деплой из GitHub |
| Backend + PostgreSQL | **Render** (или Supabase, если не нужен свой FastAPI-процесс отдельно) | Managed Postgres + 750ч/мес бесплатно, признанная замена Heroku |
| CI/CD | **GitHub Actions** | Неограниченно для публичных репо, встроено в тот же репозиторий |
| Локальная разработка | **Docker Compose** (api + worker + redis + postgres) | Один `docker-compose up`, среда одинакова у всех |
| Error tracking | **GlitchTip** (self-host или их бесплатный облачный тариф) | Open-source, Sentry-SDK-совместим — реальный enterprise-паттерн (централизованный трекинг ошибок), бесплатно |
| Аналитика (не приоритет) | Яндекс.Метрика / Plausible / Rybbit, если понадобится | Открытые/доступные альтернативы Google Analytics |

Контейнеризация (Docker) и оркестрация — прямое попадание в `Часть 2/Модуль 05. Деплой и DevOps` (Docker, CI/CD, облачные модели) — ещё одно место, где «энтерпрайз» и «то, что реально по программе» совпадают, а не конфликтуют.
