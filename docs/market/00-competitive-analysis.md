# Анализ рынка и аналогов

**Статус:** актуально (данные о конкурентах сверены через веб-поиск на 2026-09-17, не только по памяти)
**Связанные документы:** [`../requirements/00-overview.md`](../requirements/00-overview.md), [`../architecture/00-system-architecture.md`](../architecture/00-system-architecture.md)

## 1. Зачем этот документ

Стандартный раздел РПЗ «Обзор аналогов» требует не просто перечислить конкурентов, а показать, чем продукт отличается и почему решение оправдано — то есть именно то, что определяет позиционирование DiagramCode. Ниже — реальные существующие инструменты той же категории (diagram-as-code / диаграмма-редакторы), сгруппированные по типу, с честной оценкой сильных и слабых сторон каждого, а не только «мы лучше».

## 2. Категории рынка

Рынок инструментов для диаграмм распадается на три непересекающихся подхода:

1. **DSL/текст → диаграмма** (та же категория, что DiagramCode): PlantUML, Mermaid, D2, Graphviz/DOT, NomNoml, WebSequenceDiagrams.
2. **GUI-первые редакторы** (мышь, не текст): draw.io/diagrams.net, Lucidchart, Miro/FigJam, yEd, Excalidraw.
3. **Специализированные enterprise-инструменты нотаций**: Enterprise Architect, Visual Paradigm, Camunda Modeler/bpmn.io/Signavio (BPMN), Ramus Educational/BPWin (IDEF0/IDEF1X — актуальны именно в СНГ-вузовской практике), CPN Tools/PIPE (сети Петри), Structurizr (C4-модель, текстовый DSL, но только C4, не полный охват UML/ERD/IDEF).

## 4. Честный вывод: где DiagramCode реально уникален, а где — просто «ещё один»

**Уникальность не в самой идее «текст → диаграмма»** — она давно занята (PlantUML с 2009 года, Mermaid — фактический стандарт GitHub/Notion). Реальная ниша DiagramCode — **пересечение трёх свойств, которого ни у одного конкурента нет одновременно**:

1. Собственный DSL с явным git-подобным версионированием на уровне данных (Commit+Blob+дедуп), а не «файл лежит в вашем внешнем git».
2. Единый продукт, покрывающий одновременно инженерные нотации (UML, ERD, BPMN) **и** методологические (IDEF0/1X/3, DFD, сети Петри) — конкуренты почти всегда специализируются в одном из двух лагерей (PlantUML/Mermaid/D2/Eraser — инженерный лагерь; Ramus/BPWin — методологический, устаревший UX).
3. AI-генерация, встроенная в тот же цикл сохранения/версионирования, а не отдельный экспорт-импорт.

**Ближайший по духу и самый серьёзный ориентир для сравнения в РПЗ — Eraser.io/DiagramGPT**: у него уже есть DSL + AI + collab + git-интеграция + даже MCP-сервер для агентов. Честно: по зрелости и охвату Eraser сейчас обгоняет DiagramCode на текущем этапе разработки. Отличие DiagramCode от него — методологические нотации (IDEF/сети Петри), которых у Eraser нет вообще, и git-подобная модель версий на уровне собственной БД, а не как надстройка над продуктовой историей версий.

**Честная оговорка, которую стоит явно проговорить на защите**: DiagramCode на сегодняшнем этапе реализации (ERD + BPMN) уже, а не шире рынка — широта охвата нотаций пока декларативная (архитектурная возможность реестра плагинов), а не фактическая. До тех пор, пока не реализованы UML class, IDEF0, IDEF1X/3, DFD и сети Петри, честная формулировка в РПЗ — «архитектура спроектирована для покрытия N нотаций, на курсовом срезе реализовано 2» — а не «покрывает все нотации».

## 5. Что взять из анализа аналогов практически

- **У D2** — заимствовать идею качественного layout-движка (TALA/ELK) как ориентир для будущего рендера сложных диаграмм (сейчас не приоритет, но повод не изобретать layout-алгоритм с нуля позже).
- **У Eraser** — обратить внимание на MCP-сервер для агентов: это прямое концептуальное подтверждение того, что интеграция «диаграммный DSL + AI-агент» — не футуристичная идея, а уже существующий паттерн на рынке; стоит держать в уме как направление для FR-AI-* после MVP.
- **У Camunda/bpmn.io** — идея исполняемости BPMN (не просто рисовать процесс, а уметь его выполнить) — заведомо вне охвата DiagramCode, но стоит явно исключить эту идею как «сознательно не делаем», а не просто не упомянуть.
- **У Ramus/BPWin** — напоминание, зачем вообще нужны современные версии этих нотаций: устаревший UX этих инструментов — реальный, а не выдуманный аргумент в пользу проекта для методологического лагеря нотаций.
